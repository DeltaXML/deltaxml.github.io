Schematron

Schematron files (.sch) are checked as you edit them, with auto-completion and formatting. They're checked as SchXslt2 runs them: SchXslt2 is the ISO Schematron processor included with XSpec, which compiles a schema to an XSLT 3.0 stylesheet - see Testing a Schematron.

A schema is checked as ISO Schematron 2025 with an XSLT query binding, e.g. queryBinding="xslt3" - with queryBinding="xslt4", its XPath is checked as XPath 4.0. A schema in the namespace of Schematron 1.5 is reported, as SchXslt2 doesn't validate with it - with a quick fix, Convert to ISO Schematron, that changes the namespace, a pattern's name to its title, and sch:key to xsl:key.

Validating an XML file

With an XML file in the editor, run Schematron: Validate from the Command Palette - or Validate with Schematron from the More Actions (...) menu in the editor's title bar. The file is validated as SchXslt2 validates it, with the Saxon of the XSLT.tasks.saxonJar setting - any edition - and each failed assertion and successful report is shown in the Problems view, at the element or attribute it's about, with its message and diagnostics. Its severity is the assertion's severity or role - e.g. warning or info - and otherwise an error. To go to the assertion in the schema that reported a problem, click its id - or assert or report - in the problem's hover or the Problems view, use the Show the assertion quick fix (⌘.), or the link below the problem in the Problems view.

The schema is the one an xml-model processing instruction in the file associates with it, e.g. <?xml-model href="rules.sch" schematypens="http://purl.oclc.org/dsdl/schematron"?> - otherwise the one last used for the file, or one you choose from the workspace's. Schematron: Validate (Choose Schema)... chooses again. With a schema in the editor, the command validates the file last validated with it.

In the schema, the validation is shown above each rule: the nodes it fired for, with its failed assertions and reports - the nodes it was suppressed for, as an earlier rule of its pattern matched them first - or that it never fired, which usually means its context isn't what was meant. Above each pattern is how many of its rules fired, or that it wasn't active in the phase. Click one to open the XML file.

Once a file is validated, it's validated again each time it, or the schema, is saved - so you can edit the schema's rules and see what they report. Saxon's messages, e.g. for an error in the schema, are in the Schematron output channel.

The schema's default phase is used - its defaultPhase, or all its patterns without one. Schematron: Validate (Choose Phase)... chooses another: one of the schema's phases, with its title, or #ALL for all its patterns. The phase is kept for the file and the schema, and shown with the result - and above a pattern that wasn't active in it.

Saxon's syntax extensions are turned on as for the schema's XSpec tests, e.g. for xsl:note or queryBinding="xslt4", and the XSLT.resources.catalog setting is used for the files it refers to.

Editing

Auto-completion offers the elements, attributes and values ISO Schematron 2025 allows where you are - e.g. sch:group, sch:param, an assertion's severity, and a phase's from and when - with a description of each element. It works whatever prefix the schema uses for Schematron - sch, another, or none, with the Schematron namespace as the default. In a new file, it offers a schema with a pattern.

An element is inserted with the attributes it requires, in each form it's commonly written - e.g. sch:rule with context, sch:rule (abstract) with abstract="true" and id, sch:assert with test and its message, and sch:let with name and value, or its content - as are the XSLT declarations SchXslt2 copies, e.g. xsl:function with name and as.

In XPath, auto-completion offers the variables in scope - the schema's, the pattern's and the rule's - and element and attribute names from the data the schema validates: the XML file last validated with it, else an open file whose xml-model names it, else the last XML file viewed.

XPath expressions are highlighted and checked in context, test, subject, select, path, value, visit-each, documents, and a phase's from and when. role, flag and severity are attribute value templates, e.g. role="{$level}", as SchXslt2 copies them into its report.

Navigation

  • Ids - in a reference - is-a, extends's rule, a phase's active, defaultPhase, and an assertion's diagnostics and properties - auto-completion offers the ids it can refer to, e.g. the abstract rules for extends, and in a pattern with is-a, a parameter's name offers the abstract pattern's parameters. Go to Definition, Find All References and Rename work on an id, in the schema and the files it includes
  • Variables - Go to Definition, Find All References and Rename on a variable reference or an sch:let or sch:param, with the variable's scope as SchXslt2 has it - and for an abstract pattern's parameter, the sch:param of each pattern with is-a for it
  • Schematron Includes - for a Schematron file, the Imports view in the Explorer - XSLT Imports for a stylesheet - shows the schema that includes it, found from the workspace's .sch files, with the files the schema brings in: with sch:include, sch:extends's href, and xsl:include and xsl:import - each XSLT module with its own imports and includes - expanded down to the file in the editor. Click a file to open it. A file that sch:include brings in, e.g. one whose outermost element is a pattern, is checked for the XSLT SchXslt2 ignores, as a schema is
  • Outline - each element by what identifies it: a pattern by its id, a rule by its context, an assertion or report by its id, else its test

Hover help

Hover help is for reviewing a schema as much as for editing it:

  • A pattern's is-a - the abstract pattern's title, its parameters with the values this pattern gives - or their defaults - and its rules and their tests with those values in place, as SchXslt2 instantiates them
  • extends - the abstract rule's variables and tests, as they're copied into the rule
  • A rule - its context, variables and assertions, and the earlier rules of its pattern: a node is handled only by the first rule whose context matches it, so a rule that comes after a rule that matches the same nodes is never used
  • An assertion or report - when it's reported, its severity, role and flag, its message, and the text of its diagnostics
  • A variable - its sch:let or sch:param, with its value and where it's declared - or in an abstract pattern, its parameter and the value each pattern gives it
  • A phase's active, and an assertion's diagnostics and properties - the pattern's title and rules, and the diagnostic's or property's text
  • Functions - as in a stylesheet: the signature of a built-in function, and of a function declared in the schema or a module it includes, with its documentation

Checks

The problems are shown in the Problems view, as for a stylesheet:

  • Variables - sch:let and sch:param are in scope as SchXslt2 declares them: the schema's and a phase's are global, a pattern's are in scope in its rules, and a rule's in its assertions and reports
  • Namespace prefixes - SchXslt2 declares only the prefixes of sch:ns in its stylesheet, so a prefix declared only with xmlns - or not at all - is reported, e.g. xs in xs:integer(@n), with a quick fix that adds the sch:ns. Within an XSLT element, e.g. xsl:function, its xmlns declarations apply too
  • Abstract patterns and rules - an abstract pattern's parameters aren't variables, so they aren't reported, and an abstract rule and the rules that extend it share their sch:let, as SchXslt2 copies its content into each of them
  • References - as SchXslt2 resolves them, with the files sch:include brings in: an error where it stops - is-a that isn't the id of an abstract pattern (or group), or doesn't supply a parameter the abstract pattern declares with no value, and extends whose rule isn't the id of an abstract rule - and a warning where it ignores the reference: a phase's active for a pattern that isn't declared, or is abstract, diagnostics or properties that aren't declared, and ids that aren't unique. Go to Definition on a reference goes to its declaration, also in an included file
  • Files - the href of sch:include, sch:extends, xsl:include and xsl:import is a link to the file - and a file that isn't found is reported, as SchXslt2 stops
  • Rules that never fire - a node is handled only by the first rule of a pattern whose context matches it, so a rule with the same context as an earlier one, or one for elements after a rule for every element, e.g. context="*", is reported - not in a group, where every matching rule is used
  • Required attributes - an element without an attribute ISO Schematron requires is reported, with a quick fix that adds it: an error where SchXslt2 fails without it, e.g. a rule's context, an assertion's test or sch:ns's uri, and a warning where it carries on, but the element can't be referred to or does nothing, e.g. a phase with no id
  • Elements and attributes - those that ISO Schematron doesn't allow where they are. Elements in other namespaces, e.g. Schematron QuickFix's sqf:fix, aren't checked against Schematron's schema, and a file that sch:include includes may start with any Schematron element, e.g. sch:pattern

XSLT in a schema

An xsl:function, xsl:key or xsl:accumulator in the schema is checked as in a stylesheet, and its functions can be called in the schema's XPath. So can the functions of the modules that xsl:include and xsl:import bring in.

SchXslt2 copies only these XSLT declarations of a schema into its stylesheet: xsl:accumulator, xsl:function, xsl:include, xsl:import, xsl:import-schema, xsl:key and xsl:use-package. Other XSLT isn't used as written, so it's reported:

An xsl:note in a declaration SchXslt2 copies, e.g. xsl:function, is copied with it, and its stylesheet is XSLT 3.0: Saxon runs it only with its syntax extensions, which XSpec turns on for the tests of the schema - with the default XSLT.xspec.allowSyntaxExtensions setting, auto - as it does for queryBinding="xslt4". A note is reported when the Saxon of the XSLT.tasks.saxonJar setting can't run it - Saxon-HE, or a Saxon before 13 - or the setting is off, with a quick fix that adds use-when="false()", with which Saxon leaves the note out.

SchXslt2 also declares the unnamed mode, with the schema's own accumulators. An included or imported module that declares the unnamed mode with use-accumulators is reported, as Saxon reports XTSE0545 for the two, and so is one that declares accumulators, as SchXslt2's modes don't use them: declare them in the schema instead.

Text value templates in messages

A message can use text value templates instead of sch:value-of, as in XSLT: with xsl:expand-text="yes", Order {@id} has an invalid date: {@date} is Order <value-of select="@id"/> has an invalid date: <value-of select="@date"/>. It's a non-standard extension - ISO Schematron doesn't have it - so it's allowed only with the XSLT.schematron.allowExpandText setting, which is off by default. For a Schematron file, the status bar shows tvt:on or tvt:off for the setting; click it to open the setting - it's for every Schematron file, not just the one in the editor.

  • Where - xsl:expand-text is inherited, as in XSLT: on the schema, it's for every message; on a pattern, rule or assertion, for those within it - and "no" turns it off within. The xsl prefix is the one the schema declares for XSLT
  • Messages - the text of sch:assert, sch:report, sch:diagnostic and sch:property, and of sch:emph, sch:span and sch:dir within them: where sch:value-of is allowed. A title or sch:p is text
  • Braces - {{ and }} are braces in the text. Within an expression, braces and quotes are the expression's - e.g. {map { 'a': 1 }?a} or {"it's {fine}"}
  • Included files - a file sch:include brings in has its own xsl:expand-text: a file without it is unchanged, so a library's braces, e.g. in [A-Z]{2}, are still text
  • Abstract patterns - a parameter in a text value template is replaced, as in an attribute, e.g. {$attribute}

In the editor, text value templates are highlighted and checked as XPath, with auto-completion, and Go to Definition, Find All References, Rename and hover for their variables. Schematron: Validate, and the XSpec tests of a schema, rewrite them as sch:value-of before SchXslt2 compiles the schema - with the space between two of them, e.g. {@first} {@last}, kept. Without the setting, xsl:expand-text is reported as ignored, with quick fixes to remove it or to open the setting.

Other Schematron processors ignore xsl:expand-text, so the braces would be in their reports as written. For them, Schematron: Export Standard Copy... writes a copy of the schema as standard ISO Schematron: its text value templates as sch:value-of, with the files it includes in it, and paths relative to the copy. The stylesheet it uses, expand-text.xsl - in the extension's xslt-resources/schematron folder - can also be run on its own, e.g. before another processor: java -jar saxon.jar -s:schema.sch -xsl:expand-text.xsl -o:schema-standard.sch.
