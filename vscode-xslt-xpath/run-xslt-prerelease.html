Run XSLT Pre-Release

This page describes the new Quick Run command in the current pre-release build of the XSLT/XPath extension. If you are using the stable release, see the Running XSLT page instead.

Quick Run is a lighter-weight way to run an XSLT stylesheet with Saxon (Java), without first creating a task by hand. It reuses the same command-line arguments a Saxon Task would use, but takes the stylesheet and XML source directly from the editor rather than requiring a pre-configured tasks.json entry.

Running a stylesheet

With an XSLT file open in the active editor, invoke Quick Run in one of three ways:

  • Press ⌘⌥R (Ctrl+Alt+R on Windows/Linux)
  • Click the Quick Run with Saxon play button in the editor title bar
  • Run Quick Run with Saxon from the Command Palette

The stylesheet is the active editor's file. The XML source is the current XML context file - the same file used to provide XML node-names when auto-completing XPath location steps, shown in the status bar. This means the context file now serves two purposes: XPath auto-completion, and as the Quick Run source document.

The XSLT.tasks.saxonJar setting must already point at your Saxon jar file, and an XML context file must be set, before Quick Run can be used. See the Saxon (Java) setup section on the Running XSLT page for how to configure the Saxon jar path.

First use: a task is created for you

The first time Quick Run is used for a given stylesheet/context-file pairing, a real task is added to your workspace's tasks.json file (creating the file if it doesn't exist yet) - not just an ephemeral, one-off run. The generated task:

  • is labelled from the stylesheet and context file names, for example demo with books.xml
  • uses the xslt-xpath.pickResultFile command for its result path, so you're prompted to choose (or reuse a recently used) output location - the same 'recent files' behaviour described on the Running XSLT page
  • includes an entry in its parameters array for every top-level xsl:param declared with a select default - including params declared in imported or included stylesheets - ready for you to edit
Parameter values generated this way are prefixed with ?, for example ?title. This tells Saxon to evaluate the value as an XPath expression rather than a literal string, so the generated entry reproduces the parameter's own default exactly - it does not silently override it with an empty value.

Subsequent runs

Once a task exists for a stylesheet/context-file pairing, Quick Run re-runs that same task rather than creating another one. This means you can freely edit the generated task afterwards - change a parameter value, adjust the result path, add Saxon features or additional parameters - and Quick Run will keep using your edits on every subsequent run, just like running any other task.

If you want a fresh task instead, either edit the existing one directly, or remove it from tasks.json and Quick Run will create a new one next time it's used for that stylesheet/context-file pairing.

The XML context file is remembered

Your chosen XML context file is now restored automatically when Visual Studio Code is reopened, rather than defaulting back to the last XML file you happened to view. It's stored per workspace, separately from the 'recently used' file list, so viewing other XML files - for example a transform's result - does not change what gets restored.

SaxonC Tasks

A new xslt-c task type runs XSLT transforms using SaxonC, Saxonica's native C/C++ port of Saxon, alongside the existing xslt (Saxon Java) and xslt-js (Saxon-JS) task types. Its command-line arguments mirror the Saxon (Java) task closely, since SaxonC's Transform command-line tool follows the same conventions.

Setup

  1. Install SaxonC and note the folder containing its Transform (or Transform.exe on Windows) command-line executable.

  2. Set the XSLT.tasks.saxonCPath user setting to that folder.

  3. Invoke Tasks: Run Build Task from the Command Palette (⇧⌘B) and configure a new xslt-c task, following the same steps as for a Saxon (Java) task described above.

SaxonC tasks can be disabled with the XSLT.tasks.saxonc.enabled setting, matching the equivalent settings for Saxon (Java) and Saxon-JS tasks.

Native library path (macOS/Linux)

Some SaxonC distributions are built without an embedded library search path, so the native shared libraries alongside Transform - and any others it depends on - may not be found automatically. The xslt-c task always searches the lib folder next to the configured saxonCPath, and you can list additional folders (for example, a separately-packaged core library) in the saxonCLibraryPaths task property, or the equivalent XSLT.tasks.saxonCLibraryPaths user setting.

If a transform fails with an error like Library not loaded: ...dylib ... no LC_RPATH's found, add the folder containing that library to saxonCLibraryPaths.

Licensing

If SaxonC reports No license file found - running with licensable features disabled, set the licenseFileLocation task property (or the equivalent XSLT.tasks.saxonCLicenseFileLocation user setting) to the path of your saxon-license.lic file. This is passed to Transform as --licenseFileLocation:, the same option Saxon (Java) tasks use.
