Overview

DeltaXignia's XSLT/XPath extension for Visual Studio Code supports XSLT 3.0 and XPath 3.1, and the XSLT 4.0 and XPath 4.0 features implemented in Saxon 13.

The aim is to make writing, reviewing and debugging XSLT and XPath easier.

The extension understands XPath expressions within the XSLT semantically, so it can detect problems immediately, whether code is written manually or generated by an AI assistant, navigate directly to declarations across imported modules, safely rename variables, functions and templates, and step through XPath expressions in the debugger. It distinguishes variables, functions and node tests, tracks where each is declared, and uses this information throughout editing, navigation, refactoring and debugging.

For an overview of the extension's capabilities, see Features. For what's new in the latest release, see What's New.

Getting started

  1. Install the extension and open an XSLT file - editing, highlighting and checking need no setup.
  2. To run or debug stylesheets, set XSLT.tasks.saxonJar to the path of your Saxon jar (Saxon-HE is fine), with a Java runtime on the PATH - see The Saxon jar.
  3. Press ⌘⌥R (Ctrl+Alt+R on Windows/Linux) to Quick Run the stylesheet with the XML file you last had open - shown in the status bar, where you can pick another.

Writing XSLT

Problems are reported as you type - in XPath syntax, XSLT instructions, types and function calls, and references to declarations in other modules - many with a quick fix. Auto-completion offers the variables, functions, templates and modes in scope, and node names from the XML file you're working with. See Editing XSLT/XPath.

Reviewing XSLT

Hovering over a name shows its declaration - its type, and its documentation from an xsl:note - wherever it's declared. Go to Definition, Find References, the Outline and the XSLT Imports view help you find your way around a large stylesheet and its modules. See Code Navigation and Code Documentation.

Running XSLT

Quick Run runs the stylesheet in the active editor with SaxonJ, SaxonJS or SaxonC. The first run creates a task in tasks.json, which you can edit - and you're asked for the values of any required stylesheet parameters. Saxon's errors are listed in the Problems view, linked to the code. See Quick Run.

Debugging XSLT

The debugger sets breakpoints and steps through templates, functions and multi-line XPath expressions, showing variables, the context item and the output written so far. Where Saxon's standard tracing stops at XSLT instructions, this debugger uses Saxon's own APIs to inject extra trace points and re-parse XPath to locate sub-expressions, so it can stop deep inside multi-line expressions and inline functions. See Debugger.

Scope

The extension supports the XSLT 4.0 and XPath 4.0 features that Saxon 13 implements. Its checks are made as you type, without compiling the stylesheet - Saxon reports anything else when the stylesheet runs. Schema-aware features aren't supported. The debugger needs SaxonJ 12 or later (any edition); SaxonJS and SaxonC stylesheets can be run, but not debugged.

Run XSLT - Quick Start

The quickest way to run the stylesheet in the active editor is Quick Run: press ⌘⌥R (Ctrl+Alt+R on Windows/Linux) or click the play button in the editor title bar. The first run creates an XSLT task for you, which later runs reuse.

To step through the stylesheet instead, set a breakpoint and click the debug button in the editor title bar, or press F5 when there's no launch.json - see the Debugger.

XSLT transforms are run using Visual Studio Code Tasks. Before configuring an XSLT task you should ensure that you open a Workspace folder (⌘O) from Visual Studio Code. The configuration is saved in a tasks.json file in this workspace folder.

To create your first task, use the Run Build Task command (⇧⌘B). As there is no currently configured task, you should be prompted to configure one (if another extension inhibits this, run Configure Task instead). You can then select the Saxon Transform (New) (SaxonJ), Saxon-JS Transform (New) (SaxonJS) or SaxonC Transform (New) (SaxonC) task.

A task will be added to the tasks.json task with default properties. To further configure the task, these properties can be changed or other properties added. Auto-completion and hints are provided to assist in the task configuration. Next time you press ⇧⌘B your task will be run in a Task tab in the Terminal window (toggled with ⌘J).

More on running XSLT

XSLT tasks are explained in full on the Tasks page. More general information can be found in the Visual Studio Code Tasks documentation.

The User Interface

Visual Studio Code's user interface has a different look and feel to that of legacy XSLT editors. The Command Palette, along with keybindings to most common commands, play a significant role in providing a clearer environment to work in. User interface clutter is significantly reduced by eschewing previous designs which depended on a set of toolbars, each with an abundance of buttons.

The application menu bar and associated dropdown menus usefully group the more essential actions for managing your code. The View menu is particularly useful as it logically sets out the large set of view-configuration commands.

The sections below introduce you to the fundamental parts of the user interface from the perspective of an XSLT/XPath developer.

The Command Palette

A principal part of Visual Studio Code's user interface is the Command Palette, triggered by the keyboard shortcut ⇧⌘P. The Command Palette shows all available commands in a dropdown list. The list of commands is filtered as you type. The most recently used commands are shown at the top of the list.

Opening Workspace Files

The File: Open Folder command is used to select the starting 'Workspace' folder to be used by VS Code. More folders can be added to the Workspace subsequently using the Workspaces: Add folder to workspace command. The keyboard shortcut ⌘P provides quick-access to all Workspace files from a pick-list. 'Fuzzy-matching' allows you to type in just a part of the filename to filter the pick-list files.

Keyboard Shortcuts

While the Command Palette provides convenient access to features you should find that keyboard shortcuts are more effective for commands you use most frequently. The keyboard shortcut for commands is shown alongside each listed command in the Command Palette. Not all commands have key bindings, but these can be configured using the command Preferences: Open Keyboard Shortcuts (⌘K⌘S). See: Key Bindings for Visual Studio Code

Settings

By adding or modifying Visual Studio Settings, using the Preferences: Open User Settings command, you can customize a range of editor and extension features to meet your needs. See the Settings section for details on some of the more important settings for developing in XSLT and XPath.

Install the XSLT/XPath Extension

Extensions are managed in the Extensions view (⇧⌘X) of the Side Bar. Type XSLT XPath in the Extensions view search bar and, on the XSLT/XPath for Visual Studio Code entry, press the install button.

Color Theme Extensions

Visual Studio Code includes a small set of light and dark color themes. Alternative color themes are installed as extensions. The number of available themes can be overwhelming, but VS Code has a built-in Theme Preview feature and there are websites like vscodethemes that provide a preview before installing the theme.

The XSLT/XPath extension syntax highlighter uses Semantic Highlighting that should be enabled specifically in Settings to work with external color themes. Highlighter tokens are defined to provide effective highlighting for all the common color themes.

Viewing HTML Output

When your XSLT generates HTML, you can view the result in Visual Studio Code's integrated browser, with no extension needed. You can also choose Open in Integrated Browser from the editor title bar of an HTML file, or from its context menu in the Explorer. With the workbench.browser.autoReloadOnFileChange setting, the page reloads each time the transform writes the result file again - so you can edit the stylesheet, run it with Quick Run, and see the updated output alongside the XSLT.

Creating User and Workspace Settings

The Saxon jar

To run or debug stylesheets with SaxonJ - Saxon for Java - set XSLT.tasks.saxonJar to the full path of your Saxon jar file, usually as a user setting, since the path is specific to your computer. Any Saxon edition works, including Saxon-HE. The Debugger needs Saxon 12 or later, and a Java runtime must be on the PATH:

"XSLT.tasks.saxonJar": "/Users/me/saxon/SaxonHE12-9J/saxon-he-12.9.jar"

On Windows, write each \ in the path as \\, as JSON requires - e.g. "C:\\saxon\\saxon-he-12.9.jar". For Saxon-PE or Saxon-EE, keep the licence file, saxon-license.lic, in the same folder as the jar.

XSLT tasks refer to the setting as ${config:XSLT.tasks.saxonJar}. For downloading Saxon and Java, see SaxonJ tasks.

XSLT packages

To allow XSLT package names to be resolved to file paths, package details should be added to the setting XSLT.resources.xsltPackages. Sample XSLT package settings:

"XSLT.resources.xsltPackages": [ { "name": "example.com.package1", "version": "2.0", "path": "included1.xsl" }, { "name": "example.com.package2", "version": "2.0", "path": "features/included2.xsl" } ]

XML catalog

To resolve the href of xsl:import and xsl:include - and the URIs of fixed-namespaces - with an OASIS XML catalog, and pass the catalog to Saxon when a stylesheet is run, set XSLT.resources.catalog to the catalog file's path, relative to the workspace folder. See XML Catalogs.

"XSLT.resources.catalog": "catalog.xml"

Task types

The extension provides a task type for each Saxon processor - xslt for SaxonJ, xslt-js for SaxonJS and xslt-c for SaxonC - and all three are enabled by default. To stop a processor's tasks being offered, for example in Run Build Task, turn off its setting:

"XSLT.tasks.java.enabled": true, "XSLT.tasks.js.enabled": true, "XSLT.tasks.saxonc.enabled": true

See Tasks for configuring each task type.

XSLT 4.0 Item Types and Notes in XSLT 3.0

Saxon PE and EE 12.8 or later, run with syntax extensions, accept XSLT 4.0's named item types and xsl:note in a stylesheet with version="3.0". To edit such stylesheets with the same support as for XSLT 4.0, enable the setting XSLT.validation.xslt30ItemTypesAndNotes - it's off by default. For a team, add it to the workspace settings, in the project's .vscode/settings.json:

"XSLT.validation.xslt30ItemTypesAndNotes": true

With the setting, in an XSLT 3.0 stylesheet:

  • xsl:item-type declarations are accepted, with record(...) and enum(...) types - which can also be used directly in as attributes
  • the record and enumeration type support applies: completions of record fields, map keys and enumeration values, checks of map constructors, lookups and values, hover help, and renaming a record field
  • xsl:note needs no use-when attribute - see Code Documentation

Other XSLT 4.0 and XPath 4.0 features - such as xsl:switch, keyword arguments and fn(...) types - still need version="4.0", and are reported as errors in an XSLT 3.0 stylesheet.

Without the setting, xsl:item-type and record and enumeration types are reported as errors in an XSLT 3.0 stylesheet, and an xsl:note gets a warning unless it's excluded with use-when="false()", as an XSLT 3.0 processor reports XTSE0010 for it.

To run the stylesheets, Saxon needs syntax extensions: the --allowSyntaxExtensions:on option on the command line, or allowSyntaxExtensions="true" in a Saxon configuration file. The extension's XSLT tasks and Quick Run enable it with the default "allowSyntaxExtensions40": "auto" task property, for Saxon PE and EE.

Converting Saxon type aliases

Saxon's earlier syntax for named types - saxon:type-alias, tuple(...) types and ~name for a reference to a type alias - is ignored by Saxon 12.8 and later, which only report the references. The linter warns about a saxon:type-alias, and the command XSLT: Convert Saxon Type Aliases to xsl:item-type - also the warning's quick fix - converts them in all the workspace's files, shown for review in the refactor preview first:

  • <saxon:type-alias name="dfx:bounds" type="..."/> becomes <xsl:item-type name="dfx:bounds" as="..."/>
  • tuple(t: xs:integer, label?: xs:string) becomes record(t as xs:integer, label? as xs:string)
  • as="~dfx:bounds" becomes as="dfx:bounds"

A type alias with an extensible tuple type, e.g. tuple(a: xs:string, *), isn't converted - nor is one that references it - as XSLT 4.0 has no extensible record types. These are listed after the conversion, to convert by hand.

Editing XML

XSLT developers benefit from a set of XML editing features that are also available for any XML file. These general purpose features are described here.

XML Elements

Rename Tag

As you edit the start tag name of an element, the corresponding end tag name is changed at the same time to keep the XML well-nested.

Self-Close Element

To convert an element with a start-tag and end-tag to a self-closed element: With the cursor immediately to the left of the > at the end of the start-tag, type /. Any element contents and the end tag will be deleted automatically:

Auto-Completion

Outside of the auto-complete (intellisense) features for XSLT and XPath, a small set of snippets for general purpose XML elements is accessible from the auto-completion list:

Entities

An XML or XSLT file can declare entities in its DOCTYPE's internal subset, to use as references such as &company;:

<!DOCTYPE xsl:stylesheet [ <!ENTITY company "DeltaXignia Ltd"> ]>

Each reference is checked: it must be one of the predefined entities - &lt;, &gt;, &amp;, &quot; and &apos; - a character reference such as &#160;, or an entity the internal subset declares. When the DOCTYPE names an external DTD, or the subset uses a parameter entity reference such as %chars;, any entity name is allowed, as its declarations can't all be seen.

  • Type & to auto-complete an entity name: the declared entities, with their values, and the predefined entities
  • Hover over a reference to see its entity's value, or the file of an external entity - or, for a character reference, the character's code point, such as U+00A0
  • Go to Definition (F12) on a reference goes to its <!ENTITY> declaration

In the DOCTYPE, the names of declared entities are colored as references are, and quoted values as strings.

XML Formatting

When you have an XML file open, normal XML formatting features are available. With typical hand-edited XML, only the indentation is changed by the formatting. However, if no newline characters are found at the start of the XML file, it is assumed the contents are system generated and newline characters are added for elements that are not mixed content.

The formatter observes the normal rules for whitespace preservation in XML. So xml:space attributes affect whether indentation is preserved. Whitespace in CDATA sections and 'significant' whitespace in content inferred to be mixed content is also preserved.

XML attributes on newlines and multi-line attribute value are indented by the XML formatting provider to reflect the level of nesting.

The XML: Format XML with newlines inside mixed-content command, from the Command Palette (⇧⌘P), formats the whole file with a newline added before each start tag and end tag that doesn't already start a line, and indents the result - including inside mixed content, where whitespace is otherwise preserved.

Tab on an Empty Line

In an XML or XSLT file, pressing Tab on an empty or whitespace-only line, such as one you've clicked on, indents the line for its context, as if you had just pressed Enter, with the cursor at the end of the indentation. Elsewhere, or where the line is already indented that far, Tab works as normal. The key binding is for the Tab: Indent an Empty Line for Its Context command, and can be changed in the Keyboard Shortcuts editor.

Imports and Top-Level Stylesheets

The functions, templates, variables and other global declarations of a stylesheet's imported and included modules are used throughout the editor: by auto-completion, hover and signature help, go to definition, find references, symbol renaming and the linter.

A 'non-standalone' module - one that's imported by a parent stylesheet - often relies on declarations that only the parent imports. Without knowing the parent, those references can't be resolved: they're missing from auto-completion and hover help, and the linter reports spurious problems that may obscure real ones.

With inferred imports, the top-level ('parent') stylesheet that imports or includes the active module, directly or indirectly, is found and imported along with the module's own imports, so those references can be resolved.

A parent stylesheet opened recently in Visual Studio Code is used first. Otherwise, the parent is found from the workspace's XSLT files, which are scanned in the background the first time they're needed, so the parent doesn't have to be opened first. The scan only reads the href attributes of xsl:import and xsl:include instructions, and is kept up to date as files change. Where a module is imported by more than one stylesheet, the one in the nearest folder is used. The workspace scan can be turned off with the XSLT.resources.inferParentFromWorkspace setting.

To use a different top-level stylesheet - for example, one of two that import the same modules - run XSLT: Choose Top-Level Stylesheet... from the Command Palette, or the button in the title bar of the XSLT Imports view. The list shows the top-level stylesheets that import or include the active module, directly or indirectly: the one chosen is used for all the modules of its tree. Automatic goes back to the nearest folder, and Browse... picks any stylesheet, for the active module alone. The choices are saved for the workspace, and XSLT: Reset Top-Level Stylesheet Choices clears them all. The XSLT Imports view marks a chosen stylesheet chosen, rather than inferred.

The XSLT Imports view

The XSLT Imports view in the Explorer shows, for the XSLT module in the active editor, its top-level stylesheet - marked inferred when it was found from the workspace - with its tree of imports and includes. The tree is expanded down to the active module, which is marked current, and clicking a module opens it. The tooltip for a module lists any other stylesheets that import or include it.

The ▶ button on the top-level stylesheet runs it with Quick Run, using the current XML context file - whichever module of its tree is being edited.

XSLT Linter

The XSLT/XPath linter performs checks on your code as you type, performing symbol reference tests across all included modules. Any problems are shown in the Problems Panel and also highlighted inline with a squiggly underline for the specific token at issue.

A module that relies on its parent stylesheet's imports is checked with those imports too - see Imports and Top-Level Stylesheets.

Checks made by the linter
  1. XML Syntax
  2. XSLT/XPath Variable name references
  3. XSLT/XPath Parameter name references
  4. All other symbol name references (xsl:accumulator xsl:key etc.)
  5. Function name and arity (number of params)
  6. xsl:with-param names
  7. File locations in xsl:import xsl:include xsl:use-package
  8. Order of operators/operands in XPath
  9. Matching of brackets in XPath
  10. Presence of the context-item for expressions where it is required
  11. XSLT instructions and their attributes, and their structure - for example an xsl:choose without an xsl:when, or two xsl:with-param elements with the same name
  12. Duplicate global symbol names
  13. Attribute Value Template Syntax
  14. Text Value Template Syntax
  15. Item types on as attributes of XSLT instructions
  16. Accumulator names in use-accumulators attributes, and accumulators not used by any use-accumulators attribute
  17. Operators in patterns - or, and, eq or , outside a predicate or function call, for example match="a or b" instead of match="a | b"
  18. Duplicate keys in map constructors and in the xsl:map-entry children of an xsl:map
  19. Braced URI literals, for example Q{http://example.com}name
  20. The order of xsl:param, xsl:on-completion and xsl:next-iteration within xsl:iterate

  22. XSLT 4.0: record and enumeration types, see Records and Enums

The linter follows the XSLT rules that affect which code is valid:

  • Names of functions, templates, modes and variables are matched by namespace across modules, so modules may use different prefixes for the same namespace.
  • A module may use a prefix other than xsl for XSLT instructions, for example xslt:template.
  • Forwards compatible mode: for an element with a higher version, an unknown XSLT element with an xsl:fallback child, and an unknown attribute, aren't reported.
  • Simplified stylesheets: a literal result element with xsl:version as the outermost element.
  • A call of a function that isn't known is not reported when it's guarded by use-when="function-available('name')".

Checks on modes

A large transform may run in many modes, and a template rule applied in the wrong mode fails silently. The linter warns about:

  • An unknown mode - an xsl:apply-templates whose mode isn't declared by an xsl:mode or used by any template rule, in all the stylesheet's modules - often a typo in the mode name.
  • An xsl:apply-templates without a mode in a template rule with a mode - it applies the default mode, not the template rule's mode. This commonly happens when a template rule is added for a new mode and mode="#current" is forgotten. The quick fixes add mode="#current", or mode="#default" to show that the default mode is intended. There's no warning when the template rule's modes include the default mode - the unnamed mode, or the mode named by the innermost [xsl:]default-mode attribute - or #all, nor for a template rule within an XSLT 4.0 xsl:mode, where the enclosing mode is the default.
  • XSLT 4.0: an xsl:mode with enclosed template rules but no name, and an enclosed template rule with a mode or name attribute, or without a match.

Unused Variables

The linter detects unused variables and parameters declared in either XSLT or XPath expressions. These are highlighted by being 'grayed out' in the editor. Global variables are shown as unused if they are not referenced in the current file, the 'unused' state is not affected by imported stylesheets they may reference the same variable.

Compile-time and Run-time problems

The linter is designed to find most basic code problems due to typos or changes to referenced symbols. When XSLT is run, an attempt is made to parse error messages from the Saxon XSLT processor (shown in the Task tab of the Terminal View) so that the problem token is highlighted, and the error message is shown in the Problems view.

Advantages of using the linter to supplement compile-time error detection:

  • Improved response times (lower CPU usage) as you type
  • Improved precision on error location
  • Improved potential to report multiple errors
  • Provides warnings on unused variable references etc.

XML Catalogs

An XML catalog maps the URIs used in a stylesheet to the files they're resolved to. With a catalog, a stylesheet can import a shared library by a fixed name, such as http://example.com/xslt/strings.xsl, wherever the library's files are kept - only the catalog changes when they move. Catalogs are an OASIS standard, XML Catalogs 1.1, and Saxon supports them with its -catalog option.

The XSLT/XPath extension uses a catalog to resolve the href of xsl:import and xsl:include - so the declarations of a module imported by its catalog name are known to the linter, auto-completion, hover help and go to definition - and passes the same catalog to Saxon when a stylesheet is run.

Catalogs are useful when:

  • a team shares XSLT libraries across projects, and each project keeps its copy of a library in a different place
  • stylesheets import libraries by http: URIs, and the files should be read locally - for speed, or to work offline
  • libraries are reorganised, or a new version is tried, without editing the stylesheets that import them

To try it out, see the catalog demo.

Setting up a catalog

Set XSLT.resources.catalog to the path of the catalog file - relative to the workspace folder, or with ${workspaceFolder}. For a team, add it to the workspace settings, in the project's .vscode/settings.json:

"XSLT.resources.catalog": "catalog.xml"

The setting names one master catalog. It can hand lookups on to any number of other catalogs, with nextCatalog entries - for example, a catalog for each library.

When there's no setting, and the root of the workspace folder has a catalog.xml that's an XML catalog, you're asked whether to use it: Use adds the setting to the workspace settings, and Don't Ask Again is remembered for the workspace.

To use no catalog, and not be asked, set the setting to "".

Changes to the setting, and to the catalog files, are picked up straight away.

Catalog files

A catalog is an XML file whose root element is catalog, in the namespace urn:oasis:names:tc:entity:xmlns:xml:catalog. Each entry maps a URI - the name used in an href - to the URI of a file. A relative path in a catalog is relative to the catalog file itself.

<catalog xmlns="urn:oasis:names:tc:entity:xmlns:xml:catalog"> <uri name="http://example.com/xslt/strings.xsl" uri="lib/strings/strings.xsl"/> </catalog>

With this catalog, <xsl:import href="http://example.com/xslt/strings.xsl"/> imports lib/strings/strings.xsl. The name needn't be a real web address: it's an identifier for the library.

The extension uses these entries:

  • uri - maps one URI, its name, to the URI of a file, its uri
  • rewriteURI - maps every URI that starts with its uriStartString, replacing that part with its rewritePrefix, and keeping the rest - e.g. a whole folder of libraries: <rewriteURI uriStartString="http://example.com/lib/" rewritePrefix="lib/"/> maps http://example.com/lib/strings/strings.xsl to lib/strings/strings.xsl
  • uriSuffix - maps every URI that ends with its uriSuffix to the URI of a file
  • nextCatalog - another catalog file, its catalog, to try when this catalog has no entry for a URI
  • group - groups entries, e.g. to give them an xml:base - which can also be on the catalog element or an entry, to set the base URI that its relative paths are resolved against

In each catalog, an exact uri entry is used first, then the rewriteURI entry with the longest uriStartString that matches, then the uriSuffix entry with the longest uriSuffix - and only if none matches, the nextCatalog entries, in order. An href is looked up as it's written, and then, if it's relative, as the absolute URI it resolves to.

In the editor

For an xsl:import or xsl:include whose href the catalog resolves:

  • the module's declarations are known, as for a module imported by its file path
  • Cmd/Ctrl+click on the href opens the module's file
  • hover help on the href shows how the catalog resolved it: the entry that matched, and the catalog files it was found through - e.g. Resolved by the XML catalog: the uri entry for http://example.com/xslt/strings.xsl in catalogs/libraries.xml, via catalog.xml

An href that's a URI the catalog doesn't resolve to a file is reported, naming the catalog:

  • an http: or https: URI is a warning - its declarations aren't known, but Saxon will try to fetch it when the stylesheet is run
  • another URI, e.g. urn:example:strings, is an error - Saxon can't resolve it either

In the Problems panel, the problem has a link to the catalog - and Cmd/Ctrl+click on the href opens the catalog, to add an entry for it. With no catalog, the problem suggests using one.

Catalog files in the editor

In a catalog file - one that the catalog of the setting reads, or any XML file with a catalog root element in the catalog namespace:

  • the uri of each entry, and the catalog of each nextCatalog entry, is a document link, so you can Cmd/Ctrl+click from the master catalog, through the catalogs, to a library file
  • an entry whose file - or, for a rewritePrefix, folder - isn't found has a warning, e.g. after a library has moved

Running stylesheets with the catalog

The XSLT tasks for SaxonJ (xslt) and SaxonC (xslt-c) - including those Quick Run creates - pass the catalog of the setting to Saxon, with the -catalog option, so the stylesheet is run with the same imports as it's edited with. A task's own catalogFilenames property is used instead, when it has one:

"catalogFilenames": "${workspaceFolder}/other-catalog.xml"
Saxon uses the catalog for all the URIs it resolves - including doc(), document() and unparsed-text(), and DTDs - not only imports. So the catalog is always passed, even when the stylesheet's imports don't need it.

Limitations

  • The setting names one master catalog - use nextCatalog entries for others.
  • The editor uses the uri, rewriteURI, uriSuffix and nextCatalog entries - not system, public or delegate entries, which are for DTDs and other external entities. Saxon uses them all.
  • Saxon-JS tasks aren't passed the catalog.

Catalog demo

The catalog-demo folder is a small, complete example: a master catalog that hands lookups on to a secondary catalog, which maps the URIs of two XSLT libraries, in different folders, to their files - and a top-level stylesheet that imports both libraries by those URIs. Clone the repository, or copy the files, to try it.

catalog-demo/ ├── catalog.xml master catalog: a nextCatalog entry for catalogs/libraries.xml ├── catalogs/ │ └── libraries.xml secondary catalog: a uri entry for each library ├── lib/ │ ├── strings/strings.xsl imported as http://example.com/xslt/strings.xsl │ └── dates/dates.xsl imported as http://example.com/xslt/dates.xsl ├── main.xsl imports both libraries by their catalog names └── .vscode/settings.json "XSLT.resources.catalog": "catalog.xml"

How http://example.com/xslt/strings.xsl is resolved:

  1. catalog.xml has no entry for it, so its nextCatalog entry is tried: catalogs/libraries.xml
  2. libraries.xml has a uri entry with that name, whose uri is ../lib/strings/strings.xsl - relative to libraries.xml
  3. so the import is lib/strings/strings.xsl

Try it

  1. Open the catalog-demo folder in VS Code (File > Open Folder...), so that its .vscode/settings.json applies
  2. Open main.xsl: there are no problems, and hover help on str:shout shows the function's signature, from strings.xsl
  3. Hover on an href, to see the entry that resolved it - and Cmd/Ctrl+click it, to open the library file
  4. Open catalog.xml, and follow its links to catalogs/libraries.xml and the library files
  5. Run main.xsl with Quick Run: the result is e.g. CATALOGS WORK! | Wednesday 30 September 2026

Then:

  • Change an href to a URI that isn't in the catalog, e.g. http://example.com/xslt/missing.xsl, to see the warning - and Cmd/Ctrl+click it to open the catalog
  • Move lib/dates to another folder: its entry in catalogs/libraries.xml has a warning. Update the entry's uri - main.xsl doesn't change
  • Replace the two uri entries with the rewriteURI entry in the comment in libraries.xml, and change the hrefs in main.xsl to match
  • Delete .vscode/settings.json and reopen the folder, to be offered catalog.xml

From the command line, the same catalog is passed to Saxon with -catalog:

java -cp saxon-he-13.0.jar net.sf.saxon.Transform -xsl:main.xsl -it -catalog:catalog.xml

Quick Run

Quick Run is the fastest way to run an XSLT stylesheet, without first creating a task by hand. It can run the stylesheet with any of the three Saxon processors: SaxonJ (Java), SaxonJS (JavaScript) or SaxonC (native C/C++). It reuses the same command-line arguments the corresponding XSLT task would use, but takes the stylesheet and XML source directly from the editor rather than requiring a pre-configured tasks.json entry.

Running a stylesheet

With an XSLT file open in the active editor, invoke Quick Run in one of three ways:

  • Press ⌘⌥R (Ctrl+Alt+R on Windows/Linux)
  • Click the play button in the editor title bar - its tooltip names the processor currently in use, for example Quick Run with SaxonC
  • Run Quick Run with Saxon from the Command Palette

The stylesheet is the active editor's file. The XML source is the current XML context file - the same file used to provide XML node-names when auto-completing XPath location steps, shown in the status bar. This means the context file now serves two purposes: XPath auto-completion, and as the Quick Run source document.

An XML context file must be set before Quick Run can be used - unless the stylesheet declares an xsl:initial-template, which Quick Run then starts from (see Starting from xsl:initial-template below). Each processor also needs its own setup:

  • SaxonJ - the XSLT.tasks.saxonJar setting must point at your Saxon jar file. See the Saxon (Java) setup section on the XSLT Tasks page.
  • SaxonJS - requires a NodeJS installation; the xslt3 package is run using NPX. See the Saxon-JS Tasks section on the Tasks page.
  • SaxonC - the XSLT.tasks.saxonCPath setting must point at the folder containing the SaxonC Transform executable (Transform.exe on Windows). See the SaxonC Tasks section on the Tasks page for setup details, including native library paths and licensing.
Tasks for each processor can be turned off with the XSLT.tasks.java.enabled, XSLT.tasks.js.enabled and XSLT.tasks.saxonc.enabled settings. Quick Run reports an error if the selected processor's tasks are disabled.

Running a module that another stylesheet imports

A module that another stylesheet imports or includes may use functions, variables or templates declared in other modules of that stylesheet. In the editor, these references are resolved through the top-level stylesheet - see Inferred Imports - but the module can't be compiled, and so can't be run, on its own.

When you Quick Run such a module, it's checked first - with the modules it imports and includes - and if it depends on the top-level stylesheet, you're offered the choice:

  • Run top-level stylesheet - runs the top-level stylesheet instead, with the same XML context file and processor
  • Run Anyway - runs the module itself

The choice is remembered for the module until Visual Studio Code is restarted. A module that can be run on its own is run straight away, with no prompt. The top-level stylesheet can also be run from the ▶ button in the XSLT Imports view, whichever of its modules is being edited.

Choosing the processor: SaxonJ, SaxonJS or SaxonC

Quick Run uses SaxonJ by default. When an XSLT or XML file is active, the processor currently selected is shown in the status bar, for example ▶ SaxonJ. To switch processor, use any of the following:

  • Click the processor name in the status bar
  • Hold ⌥ (Alt on Windows/Linux) and click the play button in the editor title bar - while the key is held, the play button changes to a 'switch' button
  • Run XSLT: Quick Run: Switch Processor from the Command Palette

Each of these shows a list of the three processors to pick from, with the current one marked. The play button's tooltip and the status bar update straight away.

The choice is stored in the XSLT.tasks.quickRunProcessor setting, whose values are the task types: xslt (SaxonJ), xslt-js (SaxonJS) and xslt-c (SaxonC). You can also edit this setting directly, either as a User setting or as a Workspace setting - for example, to always use SaxonC for one project. Switching processor updates the setting where it is already defined (the workspace folder, then the workspace), otherwise it updates your User settings.

SaxonC, a native executable, starts much faster than SaxonJ, which needs a few hundred milliseconds to start the Java VM and load Saxon on each run. So SaxonC usually gives the quickest turnaround when running a stylesheet on small or medium inputs. For longer transforms, SaxonJ's Java JIT compiler makes it faster: in our tests, SaxonJ was ahead once execution took more than about two seconds.

First use: a task is created for you

The first time Quick Run is used for a given stylesheet/context-file pairing, a real task is added to your workspace's tasks.json file (creating the file if it doesn't exist yet) - not just an ephemeral, one-off run. The generated task:

  • is a normal task for the selected processor: an xslt task for SaxonJ, an xslt-js task for SaxonJS or an xslt-c task for SaxonC
  • is labelled from the stylesheet and context file names, for example demo with books.xml. SaxonJS and SaxonC task labels have the processor name added, for example demo with books.xml (SaxonC)
  • uses the xslt-xpath.pickResultFile command for its result path, so you're prompted to choose (or reuse a recently used) output location - the same 'recent files' behaviour described in the Variable References in Tasks section of the XSLT Tasks page
  • refers to the processor's setting (for example ${config:XSLT.tasks.saxonCPath}) rather than copying its current value, so the task keeps working if you later change the setting
  • includes an entry in its parameters array for each stylesheet parameter that must be set - including those declared in imported or included stylesheets. Parameters with a default are left out, so the stylesheet's own defaults apply

Required parameters

A stylesheet parameter must be set when it has required="yes", or when it has no default (no select attribute or content) and an as type that doesn't allow an empty sequence - for example as="xs:string" or as="element()+", but not as="xs:string?". A parameter without an as attribute defaults to a zero-length string, so it isn't added.

The value of each one comes from an input that's added to the inputs of tasks.json, so you're asked for it each time the task runs:

"parameters": [ { "name": "title", "value": "${input:xsltParam-title}" }, { "name": "?config", "value": "${input:xsltParam-config}" } ] ... "inputs": [ { "id": "xsltParam-title", "type": "command", "command": "xslt-xpath.enterParameterValue", "args": { "name": "title", "type": "xs:string", "xpath": false } }, ... ]

You can type a value, or pick one you've used before for a parameter of that name - the last one used is first, so Enter uses it again. Press Escape to cancel the run. Once you've settled on a value, you can replace the ${input:...} reference with the value itself. Parameters with the same name, in different tasks, share an input.

For an atomic type, such as xs:string, xs:integer or xs:anyURI, the value is typed as it is, without quotes - Saxon converts it to the declared type. For other types, such as maps, arrays and nodes, the parameter name is prefixed with ?, for example ?config, which tells Saxon to evaluate the value as an XPath expression: map{'a': 1}, doc('data.xml'), or 'text' for a string.

Subsequent runs

Once a task exists for a stylesheet/context-file pairing, Quick Run re-runs that same task rather than creating another one. This means you can freely edit the generated task afterwards - change a parameter value, adjust the result path, add Saxon features or additional parameters - and Quick Run will keep using your edits on every subsequent run, just like running any other task.

Editing the task

To go straight to the task for the stylesheet and the current XML context file, use Edit Quick Run Task from the drop-down menu beside the editor's Run and Debug button. The same link is in the tooltip of the XML context file in the status bar, and the command XSLT: Edit Quick Run Task is in the Command Palette. This opens tasks.json with the task highlighted - if there isn't a task yet, it's created first, as Quick Run would create it.

Debugging always uses the SaxonJ (xslt) task, so with SaxonJ selected the menu item is Edit Quick Run and Debug Task (SaxonJ). With SaxonJS or SaxonC selected, there's a separate Edit Debug Task (SaxonJ) item. When Quick Run or debugging first creates a task, a notification also offers Edit Task.

For different sets of parameters, copy the task in tasks.json and give the copy a new label. When more than one task is for the stylesheet/context-file pairing, Quick Run (and debugging) asks which task to run - the tasks you've used most recently are listed first.

Tasks are kept separately for each processor. If you switch processor, the next Quick Run for the same stylesheet/context-file pairing creates a new task for that processor; your existing tasks for the other processors are left unchanged, and are used again if you switch back.

If you want a fresh task instead, either edit the existing one directly, or remove it from tasks.json and Quick Run will create a new one next time it's used for that stylesheet/context-file pairing.

An alternative way to run a task created with Quick Run is to invoke the Tasks: Run Task command from the Command Palette, this will list all your tasks in a pick list. The tasks are sorted with the most recently run tasks at the top.

Starting from xsl:initial-template

A stylesheet that declares an xsl:initial-template can be run with no source document at all. When no XML context file has been set yet, Quick Run does this automatically. To keep running without a source document once XML files are opened - which otherwise become the context file - click the XML context file in the status bar and choose None, the last entry in the list of files. The status bar then shows [no XML context].

With no XML context file, Quick Run starts the stylesheet from xsl:initial-template (Saxon's -it command-line option) instead of applying templates to a source document. The xsl:initial-template can be declared in the stylesheet itself or in any module it imports or includes. If there isn't one, Quick Run reports an error and offers to pick an XML context file instead.

The task created for this has an empty xmlSource and an empty initialTemplate property, and is labelled with the stylesheet name, for example report with xsl:initial-template. It is kept separately from any task for the same stylesheet that has an XML source, so you can switch between the two just by changing the context file.

None stays selected until you pick a file again - opening or viewing other XML files does not replace it. While it is selected, XPath auto-completion has no source document to take element and attribute names from.

A stylesheet can declare xsl:initial-template and also contain match templates designed for a source document, so Quick Run doesn't guess which way to run it: while an XML context file is set, it always applies templates to that file. The first time it creates a task for such a stylesheet, a notification points out the alternatives - add "initialTemplate": "" to the task to start from xsl:initial-template with the context file as the global context item, or choose None to run with no source document at all.

Running from an XML file

Quick Run can also be started from an XML file, to run a stylesheet on it without opening the stylesheet first. With an XML file open in the active editor, invoke it in one of three ways:

  • Press ⌘⌥R (Ctrl+Alt+R on Windows/Linux)
  • Click the play button in the editor title bar
  • Run XSLT: Quick Run: Run XSLT on this XML File from the Command Palette

This shows a list of the XSLT tasks that can run on the file, grouped as:

  • tasks for books.xml (named after the XML file) - every task whose xmlSource is this file, for any processor. This includes each task Quick Run has created for a stylesheet with this file as its source, so any stylesheet you've already run on the file is one click away.
  • tasks for the current file - tasks whose xmlSource is ${file}, which Visual Studio Code replaces with whichever file is active when the task runs. Use this for general-purpose stylesheets you want to run on any XML file.

Breakpoints

A breakpoint can be set on a line where an XSLT instruction or a literal result element starts. A breakpoint anywhere in a multi-line start tag is moved to the tag's first line.

Breakpoints can also be set inside a multi-line XPath expression - see Stepping through XPath.

Conditional breakpoints and hit counts

Right-click in the margin and choose Add Conditional Breakpoint... - or right-click an existing breakpoint and choose Edit Breakpoint:

  • Expression - an XPath expression, evaluated where the breakpoint is, with its variables and context item, e.g. @customer = 'Grace' or $total gt 30. If the expression raises an error, execution pauses and the error is shown.
  • Hit Count - 5 or ==5 (the 5th hit), >5, >=5, <5, <=5 or %5 (every 5th hit). With an expression too, only the hits where the expression is true are counted.

An expression and a hit count can be given for a logpoint too, to choose when it writes its message.

Logpoints

A logpoint writes a message to the Debug Console without pausing - print debugging without changing the stylesheet. Right-click in the margin and choose Add Logpoint..., or edit a breakpoint and choose Log Message.

Each {xpath} in the message is replaced by its value, evaluated where the logpoint is, e.g. {$line/@product} costs {f:line-total($line)}. Values are formatted and colored as xdm:trace() writes them, without the stylesheet including the xdm-view library:

  • a node or JNode with its path above it, showing where it's from
  • a string quoted, and a value's type where it isn't obvious, e.g. 2026-10-27 (xs:date)
  • a map or array over several lines, e.g. order: {$order}

An expression can't contain braces, as in a map constructor.

Logging all variables: {$*} is a special case - it's replaced by the local variables in scope at the logpoint, as xdm:debug-color() writes them: a banner with the name of the template, function or instruction, then each variable's name and value, e.g. order {@id}: {$*}. It's like an xsl:message with xdm:debug-color(), but without changing the stylesheet. With Saxon 12, whose maps don't keep their order, the variables may not be in the order they're declared.

Function and named-template breakpoints

To stop whenever a stylesheet function or named template is called, without finding where it's declared, click + (Add Function Breakpoint) in the Breakpoints view and enter its name. The function or template can be in any module of the stylesheet, including imported and included modules. Execution stops at the start of the function or template, where the Variables view shows its parameters - for a named template, these are the values passed to it.

  • The name is written as it is where the function or template is declared, with the same prefix, e.g. f:total or cell - or as an EQName, e.g. Q{urn:f}total. A () after the name is allowed.
  • An arity selects one version of a function, e.g. f:total#2. With no arity, every version of the function stops.
  • Conditions and hit counts work as for line breakpoints - right-click the breakpoint and choose Edit Condition or Edit Hit Count. The condition can use the parameters, e.g. $n = 2.

A name that isn't valid is shown as unverified straight away. A function or template that isn't in the stylesheet - or a function with no version of the arity given - is shown as unverified once the stylesheet has compiled; hover over the breakpoint for the reason. Template rules - templates with a match attribute - aren't stopped at this way, even when they also have a name: use a line breakpoint instead.

Pausing on errors

The Breakpoints view has two options for errors. Like the No Template Matched option, they're listed once a debug session has been started in the workspace:

  • Dynamic Errors (on by default) - pauses where a dynamic error that ends the transform is raised, including xsl:message with terminate="yes". The error's code and message are shown, and the variables at that point can be inspected.
  • Errors Caught by xsl:try (off by default) - also pauses at errors that an xsl:try catches. This needs Saxon 12.5 or later.

A static error - one Saxon finds when it compiles the stylesheet - can't be paused at, as the stylesheet never runs. This includes a type error that Saxon can tell will always happen: for example, an xsl:variable with as="xs:string" whose select is count(...), which is always an xs:integer. The session then ends with a notification that gives the first error and its line, and the errors are listed in the Problems view.

Elements no template matched

When no template rule matches an element processed by xsl:apply-templates, XSLT's built-in template rules apply: the element's text is written to the output, and its children are processed. This is often intended - e.g. for a wrapper element - but it's also what happens when a template's match pattern is wrong, e.g. for an element in another namespace, so the expected template is never used.

With the No Template Matched option in the Breakpoints view (off by default), execution pauses at the first element of each name, in each mode, that no template rule matched. It pauses at the xsl:apply-templates instruction, in a call stack frame such as no template matched: item (mode #default), whose context item is the element - so the Context view, Watch and the Debug Console show and evaluate that element. If no template has matched yet, from the start of the transform, the frame has no line.

Whether or not the option is on, when the transform ends the Debug Console lists the elements no template matched, e.g. ▸ Built-in template rules applied to 37 elements no template matched: item ×30 (mode #default), o:note ×7 (mode summary). Elements dropped by a mode with on-no-match="deep-skip" are listed on a line of their own. Modes whose on-no-match copies or skips elements otherwise - e.g. shallow-copy - aren't included, as there that's the intent; with on-no-match="fail", it's a dynamic error.

Stepping

The debug toolbar has the usual Continue (F5), Step Over (F10), Step Into (F11), Step Out (⇧F11), Pause and Stop commands. In XSLT terms:

  • Step Over goes to the next line in the current template or function, without stopping in the templates and functions it calls - for example, with xsl:apply-templates or xsl:call-template.
  • Step Into stops in each template rule, named template or function called, and in a global variable when it's evaluated.
  • Step Out continues until the current template or function returns.
  • xsl:for-each, xsl:for-each-group, xsl:iterate and xsl:analyze-string have their own entry in the call stack, and are stepped like calls: Step Over runs all their iterations, Step Into stops in their body for each item, and Step Out from their body goes to the line after them. A breakpoint in the body still stops; after stepping over one by mistake, Step Back goes back to it.

Stepping goes line by line: execution stops once each time it reaches a line, not once for each instruction on it. A breakpoint in a loop stops once for each iteration.

The debug toolbar also has Step Back and Reverse Continue - see Going back - and Show Debug Output - see Output while debugging.

Stepping through XPath

A multi-line XPath expression in a select, test or value attribute - or in xsl:map-entry's key, xsl:evaluate's xpath, context-item or with-params, or the content of an XSLT 4.0 xsl:select - can be stepped through. An xsl:when's test is stopped at where it's evaluated: only the tests reached, in order, until one is true. In XSLT 4.0, the select of an xsl:when or xsl:otherwise, and an xsl:if's then and else, are stepped through only when that branch is taken; an xsl:record's attributes - its fields' expressions - are stepped through as the record is built. Within xsl:catch, the $err: variables can be used, as in Watch. An xsl:with-param's select is stepped through as part of the instruction it's in, e.g. xsl:call-template. An xsl:sort's select is stopped at for each item, as its sort key is computed - before the first item is processed - with that item as the context item. Use Step Into at the instruction, or set a breakpoint on a line of the expression. Execution stops on each line where a part of the expression starts. A breakpoint on a line with only keywords such as then, else or return, and no expression starting on it, is unverified.

Step Into goes through an expression when that shows more than its result: when it binds variables (for, let, some or every), calls a stylesheet function or an inline function, or has an if whose branches are on lines of their own - execution then stops at the branch taken. Otherwise - for example, for comparisons joined by or - Step Into steps over it, and the variable's value is shown when it's in scope. A breakpoint on a line of the expression still stops there.

A simple map (!), a path step (/) or a predicate ([...]) is evaluated for each item of the expression before it. A breakpoint on a line of its right-hand side, or predicate, stops for each item, with that item as the context item and its position() and last() in the Context section. Step Into goes through such a loop only when what's evaluated for each item has something to show, as above - e.g. a function call - so that it doesn't stop for each item of a long path. A function argument that Saxon evaluates lazily - within the function, when it's first used - shows its context item, but position() and last() as (not known).

The expression is evaluated separately, in the instruction's context, so that each part reports its own line. It appears in the call stack as, for example, xsl:variable/@select (XPath), and its result is shown in the Debug Console, e.g. ▸ $line-totals (xsl:variable/@select, lines 25-28) returned (6.75, 10.8, 15.75) - or the dynamic error it raised, e.g. one an xsl:try catches. The instruction itself then runs as usual, but without stopping again in the functions the expression calls, or writing their xsl:message output again - so each is stopped in, and its messages written, once. The body of an inline function is stepped through each time it's called - for example, by fold-left().

Going back

The debug toolbar also has Step Back and Reverse Continue, for going back to an earlier point in the transform without starting a new debug session:

  • Step Back goes to the line reached before, in the current template or function - or, at its first line, to the line that called it.
  • Reverse Continue goes back to the last line with a breakpoint that was reached (breakpoint conditions aren't checked), or to the start of the transform if there's none.

To go back, the debugger runs the transform again, from the start, to that point - quietly, and stepping as before - then pauses there. Variables, the context item, Watch expressions and the call stack are then as they were at that point, and stepping or continuing goes on from there. xsl:message output and logpoint messages already shown in the Debug Console aren't shown again.

Call stack

The Call Stack view has a frame for each:

  • template rule, with its match pattern and mode, e.g. xsl:template match="order" mode="summary"
  • named template, e.g. xsl:template name="header"
  • function, by name and arity, e.g. f:line-total#1
  • global variable or parameter being evaluated, e.g. xsl:variable $orders
  • xsl:for-each, xsl:for-each-group, xsl:iterate or xsl:analyze-string instruction, with its select expression
  • XPath expression being stepped through, e.g. xsl:variable/@select (XPath)

Selecting a frame shows its location in the editor, and its variables in the Variables view.

Variables

The Variables view has four sections:

  • Locals - the parameters of the template, function or xsl:iterate, then the variables in scope - from xsl:variable, and from XPath for, let, some and every expressions, including a positional at $pos variable. Tunnel parameters are shown as $name (tunnel). A value that Saxon hasn't evaluated yet, and whose evaluation would run stylesheet code - for example, with Saxon 12, the accumulator passed to a fold-left function - is shown as (not evaluated yet), with a button to evaluate it. Evaluating it runs that code straight away, without stopping at its breakpoints. Inside an inline function, only the function's parameters, the variables from outside it that it uses, and its own range variables are shown.
  • Context - the context item (.), position() and last(), and where they apply, current-group(), current-grouping-key() and each regex-group().
  • Globals - the global variables and parameters, sorted by name. A global variable that hasn't been used yet is evaluated when it's shown. While a global variable is being evaluated, one that might use it - directly, or through a function - isn't evaluated, and is shown as (not evaluated yet): evaluating it would be a circular reference.
  • Output - which result is being written to, or that a temporary tree is being built (for example, an xsl:variable's content), and the end of each output written so far.

Nodes, maps, arrays and sequences can be expanded. An element shows its attributes, then its child nodes, with the line number of the element in its source document. Long values are truncated, and an expanded value shows at most 1000 items.

Inline values

While paused, the value of each variable declared earlier in the current template or function is shown at the end of the line where it's declared. This applies to xsl:variable and xsl:param, and in XPath, to let, for, some and every variables and inline function parameters.

The VS Code user setting debug.inlineValues turns inline values on or off. A change applies from the next debug session, not the one that's running.

Empty steps in paths

While paused, in the paths and lookups before the line paused at, the first step whose result is empty is faded - like an unused variable - so it's easy to see where a path stops matching. For $doc/orders/order/item, when $doc has no orders element, orders is faded. A step (after / or //), a predicate ([...]) and a map or array lookup (?key) can each be faded. Hovering over it says why it's empty:

  • for a step, how many nodes there were to select from, and any with the same name in another namespace, or the same name with different case - otherwise their names
  • for a predicate, how many items it removed
  • for a lookup, the map's keys, or the array's size

The paths checked are those in the template or function paused in (or the global variable, if paused while it's evaluated), on lines up to the one paused at. A relative path is checked when it's evaluated with the same context item as the instruction paused at - not within an xsl:for-each that's ended, for example, or a predicate. A path is evaluated as a Watch expression is, each step once, from the variable, root (/), parenthesized expression or function call it starts with. A path that starts with a call of a stylesheet function calls it once more, which may write xsl:message output again; a path isn't checked beyond a stylesheet function called after its start. Checking stops after about 300ms at each pause, so a slow path doesn't slow down stepping.

Watch, hover and the Debug Console

While paused, type an XPath expression at the prompt at the bottom of the Debug Console and press Enter to evaluate it - for example, line[@qty gt 1]/@product on an order element, or count(current-group()) in xsl:for-each-group. Expressions added to the Watch view are evaluated in the same way, and again each time execution pauses.

Expressions are evaluated in the context of the call stack frame selected in the Call Stack view, with:

  • the variables in scope, and the context item
  • the stylesheet's namespace declarations and functions, e.g. f:line-total($line)
  • current(), current-group(), current-grouping-key() and regex-group(), which give their values where execution is paused

Results are shown, and can be expanded, as in the Variables view. Hovering over a variable reference such as $total, or the name in a variable declaration, shows its value.

Formatted values with xdm:trace()

If the stylesheet includes the xdm-view library - see Print Debugging - its xdm:trace() function can also be used while debugging, to see a value formatted and colored over several lines, as in a terminal. In the Debug Console, for example, xdm:trace($order, 'order') writes the formatted value, and gives the value as its result. A logpoint doesn't need it: its message formats values in the same way already.

Use xdm:trace() rather than xdm:debug() or xdm:debug-color() here: those give the formatted text as a string, which the Debug Console shows as a short, quoted value, without color.

Output while debugging

The output written so far - the principal result, and each xsl:result-document - can be shown beside the stylesheet while paused, and is updated at each pause. It's serialized by Saxon as the result is, but indented for readability, and shown in the language of its output method: XML, HTML, JSON or plain text. The result itself is written as the stylesheet specifies.

  • XSLT: Show Debug Output, or its button on the debug toolbar, opens the output at any time - the output being written to, or, when none is and there's more than one, the one you choose.
  • To open the output automatically, at the first pause where there is some, turn on the XSLT.debug.openOutput setting - it's off by default.
  • Show Output, on the context menu of an output in the Variables view's Output section, opens that output.
  • xsl:message output, and the result when there's no resultPath, are written to the Debug Console.

XML output can be traced back to the stylesheet. With the cursor on a line of the output, a hint at the end of the line - e.g. → report.xsl:4 - shows where that part of the output was written. To go there, use Go to XSLT Source on the output's context menu, Cmd/Ctrl-click, or F12 - or Option/Alt-click, when editor.multiCursorModifier is ctrlCmd. The stylesheet is shown in another editor group from the output's. For HTML, JSON or text output, Go to XSLT Source reports that only XML output can be traced back to the stylesheet.

When the session ends, a notification offers to Open the result file - or, for HTML, to Open in Browser.

Saxon errors

Saxon's error messages in the Debug Console are linked to the location of the error. The errors are also listed in the Problems view, as for XSLT tasks. A file's errors are removed from the Problems view when the file is edited, as they may no longer apply.

When the transform fails, the notification at the end of the session gives Saxon's reason - for example, that the XML source file doesn't exist - or, for a dynamic error, its message, code and line. For a stylesheet with static errors, which can't be debugged, it gives the first of them.

Sample: stepping through XPath

The debugger-demo sample has a stylesheet, debug-xpath.xsl, and an XML file, orders.xml. Open orders.xml, so it becomes the XML context file, then debug-xpath.xsl, and start debugging. Things to try are listed in a comment at the top of the stylesheet, including:

  • stepping through a multi-line for ... return expression, and into a function it calls
  • a breakpoint inside an expression in xsl:for-each-group, with count(current-group()) in the Watch view
  • conditional breakpoints, hit counts and a logpoint
  • pausing at a dynamic error, after changing a price in orders.xml to n/a

Limitations

  • For debugging, the stylesheet is compiled without optimization, so all variables can be inspected. Saxon still evaluates constant expressions when it compiles - e.g. an xsl:if whose test uses only constant values - and an instruction removed that way can't be stopped at.
  • Values can't be changed in the Variables view.
  • Going back relies on the transform running the same way again; current-dateTime() is kept the same. A transform that reads a document that changes in the meantime, or calls an extension function with side effects, may not - then it runs to the end, with a notification. Breakpoint hit counts aren't wound back, and the output view keeps any output written after the point gone back to until it's written again.
  • An expression that's stepped through is evaluated in full - except a test, e.g. an xsl:if's, which is evaluated only as far as needed for true or false, as Saxon does. Where Saxon itself would evaluate only part of it - e.g. an xsl:iterate's select, when xsl:break ends the loop, or a variable that's only partly used - stepping through it can call more functions, and so write more xsl:message output, than a normal run.
  • With "messageEscaping": "on" in the xslt task, Saxon writes xsl:message output itself, so a message from a function called by an expression that's stepped through is written twice: once as the expression is stepped through, and again as the instruction runs.
  • Only modules loaded from files can be stopped in.
  • Saxon only evaluates xsl:assert with assertions enabled - "enableAssertions": "on" in the xslt task - so without that, its breakpoints are unverified.
  • Saxon evaluates some instructions lazily - e.g. an xsl:for-each in an xsl:map runs when the map is built - so the call stack may not show them while their content is stopped in. The context item is still the right one.
  • Accumulators: Saxon computes an accumulator's values for the whole document the first time one of them is needed - e.g. by accumulator-before() - so a breakpoint in an xsl:accumulator-rule stops for each node in turn at that point, not as each node is processed. If a breakpoint condition or a Watch expression is the first to need the values, they're computed while it's evaluated, and the rule's breakpoints aren't stopped at. Accumulator rules are reported to the debugger by Saxon 12.8 or later.
  • Keys: Saxon builds a key's index for the whole document the first time key() is called for it - so a breakpoint on an xsl:key stops for each node indexed at that point. As for accumulators, if a breakpoint condition or Watch expression is the first to need the index, it's built while that's evaluated, and the key's breakpoints aren't stopped at.

Troubleshooting

When a debug session doesn't start, a notification gives the reason, with a Show Output button - for example, when Java isn't on the PATH, the Saxon jar doesn't exist, or the Java runtime is too old for the Saxon jar.

The XSLT Debugger log, in the Output panel, shows how each session was launched: the Java command line, the Saxon product, the Java runtime and the Saxon options used.

Print Debugging

To set breakpoints and step through a stylesheet, see the Debugger.

While debugging, a logpoint can do much of what an xsl:message with xdm:debug-color() does, without changing the stylesheet or including the xdm-view library. Its message can include XPath values, formatted and colored in the same way, and {$*} writes all the local variables, with a banner. A logpoint has less flexibility, though:

  • Messages are only written while debugging, with SaxonJ - not when the stylesheet runs as a task or with Quick Run, or with SaxonJS or SaxonC.
  • There's less control over formatting: the banner always names the template, function or instruction, there's no $level indentation, and {$*} writes every local variable, not a chosen set.
  • An expression in the message can't contain braces, as in a map constructor.
  • Logpoints aren't saved with the code. VS Code keeps them for the workspace, so they can't be committed or shared with the stylesheet.

Adding xsl:message instructions is another way to debug XSLT - one that works with any Saxon processor, including SaxonJS and SaxonC, and shows how values change over a whole run. The output is written to the terminal when the stylesheet runs as a task or with Quick Run, and to the Debug Console when it's debugged, with ANSI colors kept in both. Diagnostics are added using the xdm:debug() function, from the xdm-viewer XSLT library, which renders one or more named in-scope variables to a formatted string for use in an xsl:message.

Diagnosing state of in-scope XSLT variables

There is special provision for conveniently reviewing the state of in-scope XSLT variables. This approach is outlined here.

1. Use Auto-complete for xsl:message

To assist with debugging, the XSLT editor has special auto-completion for the xsl:message instruction. Four completion items are offered when in-scope variables are found - otherwise, only xsl:message (blank):

  • xsl:message (blank) - inserts a simple placeholder, for entering your own xsl:message content
  • xsl:message - adaptive serialization - serializes the last declared variable using serialize() with the adaptive method
  • xsl:message - xdm:debug variables - lists all in-scope variables in a single xdm:debug() call
  • xsl:message - xdm:debug-color variables - as above, with ANSI-colored output

2. Review Inserted xsl:message

When xsl:message - xdm:debug variables (or xsl:message - xdm:debug-color variables) is selected from the auto-complete list, an xsl:message snippet is inserted at the cursor with all in-scope variables collected into a single XPath map, passed as the second argument to xdm:debug(). A title is inserted as the first argument: Watch: followed by the name of the element that the xsl:message is in - e.g. an xsl:function or named template - or the mode of an xsl:template. If that element has neither, the title is Watch Variables.

<xsl:message select="xdm:debug('Watch: my-function', map { 'items': $items, 'total': $total })"/>

3. Quick Fix: Include the xdm-view Library

As can be seen above, the xdm:debug() function is not initially resolvable - it will be marked as a 'problem' until its defining library is included. Put the cursor on the problem function and open Quick Fix with Cmd/Ctrl+. - or choose Quick Fix... when hovering over it.

Two Quick Fix options are offered:

  • include XSLT module for xdm:debug and xdm:trace (the preferred option) - inserts the xdm namespace declaration (http://deltaxignia.com/ns/xdm-persistence) and an xsl:include instruction referencing a workspace-local copy of xdm-view.xsl if one is found, otherwise the copy of the xdm-viewer library bundled with this extension.
  • copy xdm-view library into workspace - copies the bundled xdm-viewer library (and its xdm-persistence dependency) into an xslt-resources/xdm-view folder in your workspace, then applies the same include as above. Use this if you want the library files available locally, for example to inspect or version them alongside your own stylesheets.

4. Run XSLT and Review State in Terminal

You can now run the XSLT as normal, but you will now see the xsl:message output in the terminal window, with each in-scope variable shown under a title banner. Node values are shown with their location path and a pruned, truncated rendering, keeping the output readable for large trees.

Colorising for xdm:debug-color() should work from VS Code with all SaxonJ, SaxonC and SaxonJS versions. Because later SaxonJ versions don't support use of a built-in TextEmitter command-line option, an extension class is used instead of net.sf.saxon.Transform when invoking a transform via an XSLT task. This prevents escaping of ANSI codes used for coloring the output.
For this same reason, in SaxonC, the XML output from SaxonC is decoded prior to output to the terminal.

5. Benefits of xdm:debug() over fn:serialize()

We recommend the xdm:debug-color() function as it supplements the built-in serialize function with features that are especially important when you're interested in several variable values or the values have complex types.

The auto-complete fills in the arguments, so you rarely need to change them. The function signatures are:

xdm:debug($title as xs:string, $labels as map(xs:string, item()*)) as xs:string xdm:debug($title as xs:string, $labels as map(xs:string, item()*), $level as xs:integer) as xs:string xdm:debug-color($title as xs:string, $labels as map(xs:string, item()*)) as xs:string xdm:debug-color($title as xs:string, $labels as map(xs:string, item()*), $level as xs:integer) as xs:string
  • The output begins with a title to help locate the xsl:message in the code
  • The remaining content is structured in two columns: variable names in the first, values in the second
  • Nested maps, arrays and sequences are formatted for readability
  • Bracket-pair coloring helps identify the start/end of maps, sequences or arrays
  • A set of named variables or parameters can be serialized with a single function
  • Lexical XPath locations are shown above each node, and above each XPath 4.0 JNode, e.g. /lines/*[2]/sku - see JSON and JNodes
  • Node content is truncated when required to keep message output concise
  • Syntax highlighting helps identify types and map keys etc.
  • Values are annotated with their type where this is non-obvious
  • The optional $level argument adds indentation proportional to this value - helpful for recursive calls

Tracing a value within an expression: xdm:trace()

To see a value part-way through an XPath expression, without taking the expression apart, wrap it in xdm:trace(). Like XPath's built-in trace(), it returns the value unchanged, so the expression gives the same result, and writes it with xsl:message, after a label. Where trace()'s output is up to the processor - Saxon writes one line per item, with a map on one line - xdm:trace() writes the value as xdm:debug() does: formatted over several lines where it has structure, and in color.

<xsl:variable name="total" select="sum(xdm:trace($order/line ! (@qty * @price), 'line totals'))"/> <xsl:variable name="customer" select="xdm:trace($customers?($id), 'customer')"/> line totals: (7.5, 12, 17.5) customer: { 'name': 'Ada', 'langs': ['xslt', 'xpath'] }

To trace an existing expression, select it and choose Wrap with xdm:trace() (or Wrap with trace()) from the refactoring code actions, e.g. with ⌘.. The call's label is the expression itself, selected so you can type another. When you've finished debugging, put the cursor on a call's name - xdm:trace, trace or fn:trace - and choose Remove xdm:trace() - keep the expression to leave just the expression traced. It's kept in brackets only where it needs them to keep its meaning, e.g. (1 + 2) * 2 from xdm:trace(1 + 2, 'x') * 2.

At the start of an XPath expression, auto-completion offers xdm:trace(…, label). It's from the same xdm-viewer library as xdm:debug(), so it's marked as a problem until the library is included, with the same Quick Fix. The function signatures are:

xdm:trace($value as item()*) as item()* xdm:trace($value as item()*, $label as xs:string?) as item()* xdm:trace($value as item()*, $label as xs:string?, $useColor as xs:boolean) as item()*
  • Color is on by default. To turn it off for every call - e.g. when messages are written to a log file - set the NO_COLOR environment variable, to any value. To turn it off for one call, pass false() as the third argument.
  • Node values are shown with their location path and a pruned rendering, as with xdm:debug().
  • xdm:trace() reads the whole value before returning it, to format it. trace() may instead report the items of a lazily evaluated value one at a time as they're used - so, for example, head(xdm:trace($items)) reads all of $items.
  • In the debugger, the output is written to the Debug Console, in color.

Find Nodes with XPath

To find nodes in an XML file with XPath, write expressions in a query file, an XPath editor below the XML file, and run them one at a time. The nodes an expression finds are listed as VS Code lists references, to step through in the XML file. Other results, such as a count or a list of strings, are shown after the expression.

Requirements: SaxonJ - any edition, including Saxon-HE - set with the XSLT.tasks.saxonJar setting, and a Java runtime on the PATH. With Saxon-PE or Saxon-EE, expressions can use XPath 4.0 syntax. With Saxon-HE, they're XPath 3.1.

Opening the query file

In the editor of an XML file, click the search button in the editor's title bar, or run XML: Find Nodes with XPath... - from the Command Palette, the XML Selection submenu of the editor's context menu, or the XML: Select Element... quick pick (⇧⌘2 / Ctrl+Shift+2).

The query file, queries.xpath, opens in an editor group below the XML file, a quarter of its height. A new query file starts with an expression for the XML file's root element, such as /orders. There's one query file for each workspace, kept by VS Code, so your expressions are there next time.

With no workspace folder open, there's one query file shared by all the VS Code windows without a folder.

Writing expressions

The query file has several expressions, separated by blank lines. An expression can take several lines, with no blank line within it, and can have comments, (: like this :).

/orders //order[@status = 'late']/@id count(//item) //order [item = 'ink'] /@id

As in any XPath file, expressions are highlighted and checked as you type, and auto-completion includes the names of the elements and attributes in the XML file. Each expression is checked on its own.

Namespaces

The namespaces declared on the XML file's root element can be used without declaring them:

  • a name without a prefix matches an element in the root element's default namespace - so for <orders xmlns="urn:orders">, //order finds its order elements
  • a prefix declared on the root element, e.g. xmlns:x="urn:extra", can be used as it is: //x:note

For another namespace - one first declared further down, or with a prefix of your choosing - start the expression with a declare namespace line:

declare namespace svg = "http://www.w3.org/2000/svg"; //svg:rect

A declaration applies only to its own expression.

Inserting the location of a node

To start from a node in the XML file, put the cursor on it - on an element or an attribute - and press ⌥G / Alt+G (XML: Add XPath Location to Queries). Its location, such as /orders/order[2]/@id, is added to the end of the query file, with the cursor on it, ready to run or change. If it's already in the query file, the cursor moves to it. With the cursor on no node, the query file is just opened.

In the query file, at the start of an expression, the same location is offered by auto-completion - type /, or press ⌃Space / Ctrl+Space. It's the first suggestion, marked cursor in orders.xml. The XML file must be shown in an editor.

Running an expression

Above each expression, on the blank line before it, is ▶ Run on orders.xml, naming the XML file it runs on. Click it to run the expression, or press ⌘Enter / Ctrl+Enter to run the expression at the cursor. The text in the XML file's editor is used, including any changes not yet saved.

With no blank line before an expression, e.g. on the first line, ▶ Run is a CodeLens above it - or, with CodeLens turned off (editor.codeLens), at the start of the expression's line.

If Saxon reports an error, such as a syntax error, it's shown in the Problems panel, at the place in the expression where Saxon found it.

Results

After each expression run, its result is shown in brief, at the end of its last line:

  • → /orders/order[1]/@id (1 of 3) - the location of the first node found, and how many there are
  • = 3, or = ('pen', 'ink', 'pad') - values, written as XPath literals and cut short if they're long
  • = () nothing found - an empty sequence

Click it to see the whole result in the XPath Query output panel, with each item on a line of its own. A map, array or function is written on one line, e.g. map{"a":[1,"two",true()]} or fn:count#1 - to see part of a large map, change the expression to select it.

When the result has nodes, the XML file's editor shows the first, with the nodes listed beside it, as VS Code lists references. Click one to go to it, or press F4 / ⇧F4 to go to the next or previous node. The name of an element or attribute is selected, and for a text node, its text.

At most 5000 items of a result are shown.

Switching between XML files

Expressions run on the XML file you were last in. Click into another XML file's editor, and ▶ Run names that file: run the same expressions on it, as you would search it with Find. The checks and auto-completion in the query file follow the switch, for the new file's names and namespaces.

The results shown after the expressions are those for the file they'd run on. Switch back to an earlier file to see its results again.

This is separate from the XML context file shown in the status bar for Quick Run and tasks: switching between XML files doesn't change it.

Limitations

  • Each run starts Java, so it takes about a second.
  • Results shown after the expressions aren't kept when VS Code is closed.

AI Assistants

AI coding assistants in Visual Studio Code - such as GitHub Copilot or Claude Code - can make good use of the XSLT/XPath extension. They don't need anything special from it: the extension's problems, documentation notes and debugging output are all in forms that assistants read and write well.

Fixing problems

The problems reported by the extension's linter are standard Visual Studio Code diagnostics, shown in the Problems panel. They identify the exact symbol at issue - an unresolved variable, a function called with the wrong number of arguments, a record field that doesn't exist - so an assistant that reads the diagnostics can explain and fix them precisely, and check its own changes the same way. For example, GitHub Copilot can include the problems with #problems in a chat prompt, or fix a problem from its Quick Fix menu, and Claude Code reads them through its Visual Studio Code integration.

The problems are kept up to date for every stylesheet open in an editor - not only the active one. An assistant usually changes files while your cursor is in another, so a stylesheet it changes is checked again, whether it's shown beside the active editor or in a tab that isn't shown, and the assistant sees the problems its change caused. When it changes several stylesheets at once, each is checked with its own declarations, XSLT version and imports, so no problems are reported that aren't there.

Documentation notes

XSLT 4.0 documentation notes - xsl:note format="xdoc-md" - use Markdown with @param and @return tags, in the style of Javadoc: a format that assistants already know. An assistant can read a function's note to understand it, and can write notes too - for example, when asked to document the functions in a stylesheet. As the extension checks the @param tags against the parameters, a missing or misnamed parameter in a note is reported straight away.

Debugging output

The output of xdm:debug() in xsl:message is plain, labelled text: each variable's value in XPath syntax, with its type where it isn't obvious, and each node with its path. Copied from the terminal into a chat, it gives an assistant the actual values to reason about, rather than a description of the problem.

Running XSLT

Quick Run creates ordinary tasks in the workspace's tasks.json file, and each task shows the Saxon command line it runs in the terminal. An assistant that can run commands can run a transform in the same way.

The Agents window

Visual Studio Code's Agents window, for running agent sessions and reviewing their changes, only runs the extensions on a list chosen by Microsoft, and the XSLT/XPath extension isn't on it yet. Without the extension, XSLT files in the Agents window have plain XML highlighting, with none of the extension's features - and if Red Hat's XML extension is installed, it may report errors against its XSLT 3.0 schema. To run the extension in the Agents window, add this to your user settings - see Settings:

"extensions.supportAgentsWindow": { "deltaxml.xslt-xpath": true }

Current limitations

The extension doesn't yet provide an MCP server or language model tools, so an assistant can't ask it directly for information - for example, to check a file that isn't open, to find where a symbol is declared, to list the fields of a record type, or to show the imports of a module. Assistants that run outside Visual Studio Code, such as command-line agents, only see the extension's problems if they can read Visual Studio Code's diagnostics. Problems are only reported for files open in an editor, as by most language extensions: a stylesheet an assistant changes that isn't open has none until it's opened. Tools for assistants may be added in a future release.

XSLT 4.0

XSLT 4.0 currently comprises a set of draft proposals maintained by the W3C XSLT 4.0 Community group.

DeltaXignia's XSLT/XPath language extension provides full language support for the XSLT 4.0 and XPath 4.0 features implemented in Saxon 13, as documented here: type-aware auto-completion, checks, hover help and refactoring, as well as syntax highlighting.

Note that, given the independent release cycles for Saxon and the XSLT 4.0 draft, there will be differences between the implementation and the draft specification. Some parts of the specification are likely to change significantly before it is finalized.

We will endeavour to keep this extension up to date with the latest Saxon XSLT 4.0 implementation. Earlier versions of XSLT 4.0 will not be supported for auto-completion and linting.

Editing XSLT 4.0

The version attribute on the stylesheet root element controls the XSLT version supported by the linter and for auto-completion. When the version attribute on the stylesheet root element is set to 4.0, auto-completion for XSLT instructions and attributes and XPath functions will be included. In an XSLT 3.0 stylesheet, the linter reports XPath 4.0 syntax as an error.

For Saxon PE or EE 12.8 or later, run with syntax extensions, XSLT 4.0 item types - with record and enumeration types - and xsl:note can also be enabled in XSLT 3.0 stylesheets: see XSLT 4.0 Item Types and Notes in XSLT 3.0.

XPath files, with the .xpath extension, are always treated as XPath 4.0.

XSLT 4.0 support

The syntax highlighter, linter and auto-completion support:

  • New XPath 4.0 syntax - the pipeline -> and mapping arrow =!> operators, the method call operator =?>, e.g. $shape =?> area() - with the fields of a record type suggested after it - the × and ÷ operators, braced if expressions, map constructors without the map keyword, string templates, and the new -or-self axes
  • Literals and bindings - hexadecimal and binary numeric literals, and _ digit separators, e.g. 0xFF_FF, 0b101 and 1_000_000; QName literals, e.g. #xs:integer; positional variables, e.g. for $x at $i in $items return ...; for key and value map bindings, e.g. for key $k value $v in $map return ...; and typed for, let and some bindings, e.g. let $n as xs:integer := 3
  • New item types - choice types, such as (xs:date | xs:time), and the enum, record, fn and jnode types
  • Named item types - declared with xsl:item-type, with checks on the names used, go to definition and find references
  • Function syntax - fn and focus functions, keyword arguments such as ex:area(scale := 2), optional parameters (xsl:param required="no") and partial function application
  • Functions in no namespace - an xsl:function name without a prefix, e.g. name="double", called as double(2) - a Saxon 13 extension, not available in Saxon-HE. A function with the name and arity of a built-in function, e.g. count, replaces it in calls without a prefix, so is reported as a warning.
  • JNodes - path expressions on trees of maps and arrays, with jtree(), jkey(), jvalue() and get(...) steps
  • New instructions - snippets for xsl:switch, xsl:array and xsl:select, template rules declared within an xsl:mode (enclosed modes), and xsl:record, with its attributes completed and checked against the record type - see Building records

Features in the XSLT 4.0 draft that Saxon 13 doesn't implement - such as extensible record types - are reported by the linter.

Some of the more significant XSLT 4.0 features have their own pages:

  • Records and Enums - auto-completion, checks and refactoring for record and enumeration types, including xsl:switch on an enumeration
  • JSON and JNodes - path expressions on JSON, with auto-completion, checks and hover help for JNodes with a record type
  • Code Documentation - documenting functions and templates with xsl:note, for hover help and signature help

Running XSLT 4.0

XSLT 4.0 stylesheets run with Quick Run, or with an XSLT task. Saxon needs the --allowSyntaxExtensions:on configuration property for XPath 4.0 syntax. This is controlled by the allowSyntaxExtensions40 task property:

  • auto (the default) - on, unless the Saxon jar file, or SaxonC path, is for Saxon-HE
  • on - always on
  • off - never on
The free Saxon-HE version does not support the language extensions for XSLT 4.0. You will need to reference a Saxon-PE or Saxon-EE Jar file (with license file) in the saxonJar property of the task definition, or the equivalent SaxonC edition.

Other Editors for XSLT 4.0

The Oxygen XML editor also provides language support for XSLT 4.0, with its own bundled Saxon implementation.

While Oxygen does need to be purchased, it has the advantage of including Saxon-EE built-in, so you will not need to purchase Saxon separately. Oxygen XML provides an integrated solution for XML developers and content authors, and hosts an array of other features.

Records and Enums

XPath 4.0 adds record types, for maps with a known set of fields, and enumeration types, for strings with a known set of values. XSLT 4.0 adds the xsl:item-type declaration to give these types names.

When a variable, parameter or function result is declared with one of these types, the XSLT/XPath extension uses the declared type for auto-completion, linting, hover help and navigation - for example, to list the fields when building a map, or the values of an enumeration inside a string literal.

The extension only uses declared types - from as attributes, xsl:item-type declarations and function return types. It doesn't infer types from expressions: that is left to Saxon when the stylesheet is compiled.

These features are enabled when the stylesheet has version="4.0". See the XSLT 4.0 page for the XSLT 4.0 features supported.

For Saxon PE or EE 12.8 or later, run with syntax extensions, they can also be enabled for XSLT 3.0 stylesheets, with the setting XSLT.validation.xslt30ItemTypesAndNotes - see XSLT 4.0 Item Types and Notes in XSLT 3.0. That page also describes converting Saxon's earlier saxon:type-alias and tuple(...) syntax.

Declaring types

A record type lists its fields, each with an optional type. A field name followed by ? is optional. An enumeration type lists its values as string literals:

<xsl:item-type name="address" as="record(city as xs:string, postcode? as xs:string)"/> <xsl:item-type name="person" as="record(name as xs:string, age as xs:integer, address as address)"/> <xsl:item-type name="colour" as="enum('red', 'green', 'blue')"/>

A type can also be written inline in an as attribute, for example as="record(x as xs:double, y as xs:double)".

In an attribute value, quotes within a type can be written as references, as Saxon allows - for example as="enum(&quot;it's&quot;, 'is')" or a field name quoted with &#39; - and the extension reads them as the quotes they stand for.

Auto-completion for types

  • Within an as attribute, and after instance of, castable as and the other type operators, the names of declared item types are offered with the built-in types.
  • The record(...) and enum(...) suggestions insert a snippet with placeholders for the fields or values.

Checks on declarations

  • An item type name that isn't declared is reported, as are duplicate declarations and a type that refers to itself (directly or through other named types).
  • A duplicate field name in a record type is an error, as in Saxon. A duplicate value in an enumeration type is a warning, with a Remove duplicate enum value quick fix.
  • Extensible record types, such as record(a, *), have been dropped from XPath 4.0 and are reported as an error.

Go to Definition (F12) and Find All References (⇧⌥F12) work for item type names.

Building records

A record is built with a map constructor, or with the xsl:map or xsl:record instruction. Wherever the record type is known, the extension helps you complete the map and checks it against the type.

Map constructors

In the select attribute of a declaration with a record type, type { (or map {) and accept the suggestion to insert a complete map constructor, with an entry for each required field - when the record has optional fields, a second suggestion includes them too:

<xsl:variable name="p" as="person" select="{ 'name': __TODO.name, 'age': __TODO.age, 'address': { 'city': __TODO.city } }"/>

Each __TODO.field placeholder is reported as a warning until it's replaced with a value. A double-click selects the whole placeholder, ready to type over.

After typing , at the end of an entry, the suggestions list the fields that aren't in the map yet, including optional fields.

The xsl:map instruction

Where a record is built with xsl:map, for example in the content of an xsl:variable with a record type, typing < offers an xsl:map suggestion with an xsl:map-entry for each required field (or, as a second suggestion, for all fields). Inside an existing xsl:map, the xsl:map-entry suggestions are named after the fields not yet added, for example xsl:map-entry 'age', and the key attribute offers the field names.

The xsl:record instruction

The XSLT 4.0 xsl:record instruction builds a record from its attributes: each attribute in no namespace is a field, with an XPath expression as its value. Its record type is the type in its own xsl:as attribute, or else the declared type of its value, as for xsl:map:

<xsl:variable name="p" as="person"> <xsl:record name="'Ann'" age="42" address="{ 'city': 'Oxford' }"/> </xsl:variable>
  • Auto-completion - typing < offers an xsl:record suggestion with an attribute for each required field, e.g. xsl:record person: required fields, and a second suggestion with all fields. Within the start tag, the fields not yet added are offered as attributes, required fields first, and within the content, typing < offers an xsl:map-entry for each field not yet added. A field whose name isn't an NCName, e.g. 'first name', is added as an xsl:map-entry child.
  • Checks - as for a map: an attribute that isn't a field is a warning, a literal value of the wrong type is an error, and a missing required field is an error, with the Add missing record fields quick fix. A field can also be added by an xsl:map-entry child - and when other content may add fields, missing fields aren't reported.
  • Renaming - renaming a field renames its xsl:record attributes, and Find All References lists them.

Checks on records

  • Missing fields - a required field that's missing is an error, with an Add missing record fields quick fix that adds an entry, with a placeholder, for each one.
  • Unknown fields - an entry for a field that isn't in the record type is a warning. For a map constructor key, or an xsl:record attribute, there's a Change to 'name' quick fix for each field not yet in the map, closest name first - e.g. Change to 'name' for 'nam'.
  • Field values - a literal value of the wrong type, such as a string for an xs:integer field, is an error.
  • Duplicate keys - two entries with the same literal key are an error, in any map constructor or xsl:map, whether or not it has a record type - except in an xsl:map with a duplicates attribute, which handles them, where they're a warning.

Where the record type comes from

Maps are checked, and completed, where their type is declared:

  • the select or content of an xsl:variable, xsl:param or xsl:with-param with an as attribute - for an xsl:with-param without one, the type of the called template's parameter is used
  • the result of an xsl:function with an as attribute - its last xsl:sequence
  • xsl:sequence and xsl:select with an as attribute
  • the arguments of calls to user-defined functions, including keyword arguments such as ex:move(point := { ... }) and the left-hand operand of the arrow operators
  • a typed let binding, such as let $p as person := { ... }

Using records

Lookups

After the ? lookup operator on a value with a record type, the suggestions list the record's fields. This works for variables, calls to functions with a declared record result, and chains of lookups such as $p?address?city. A lookup of a field that isn't in the record type is a warning.

Hover and navigation

Hovering over a field name - in a lookup, a map constructor key or the key of an xsl:map-entry - shows the field's declaration. Go to Definition on a field name goes to the field in the record type.

Hovering over the name of a named item type - where it's used, or on its declaration - shows its declaration, with its values for an enumeration type. When the xsl:item-type has a documentation note, the note is shown too, and a field's @field text is shown when hovering over the field, and with the field in the auto-completion suggestions.

Renaming a field

Rename Symbol (F2) on a field name - in the record type, a lookup, a map constructor key, the key of an xsl:map-entry, an xsl:record attribute, or an @field tag of a documentation note - renames the field, and all its references. Find All References (⇧⌥F12) lists them.

  • Only the field of that record type is renamed - not a field with the same name in another record type.
  • The references are found in the stylesheet, the modules it includes or imports, and - from the workspace's modules - each stylesheet that imports or includes it, with the modules they use. So a rename in a module of types reaches the stylesheets that use them.
  • A quoted field name keeps its quotes, e.g. 'unit name'. A new name must be an NCName, unless the field's name isn't one.

Path steps on records (JNodes)

XPath 4.0 path expressions can navigate maps and arrays as trees of JNodes, e.g. jtree($p)/address/city. Field names are suggested, and checked, for steps after jtree($p)/, and after a variable declared as a JNode for a record type, such as jnode(*, person). See JSON and JNodes.

Refactoring: Extract record type

The Extract record type refactoring creates a record type from an existing map - for example, when updating code written for XSLT 3.0. It's offered when the stylesheet has version="4.0", or with the XSLT.validation.xslt30ItemTypesAndNotes setting:

  1. Select a map constructor or xsl:map whose keys are string literals - or simply place the cursor on the start tag of the xsl:variable, xsl:param, xsl:with-param, xsl:function, xsl:sequence or xsl:select that it's the value of.
  2. Open the refactorings with the 💡 light-bulb, or ⌘., and choose Extract record type.
  3. An xsl:item-type declaration is added for the record type, and the declaration's as attribute is set to it - replacing a generic type such as map(*). Field types are taken from literal values, and a nested map becomes a nested record type.
  4. The new type is named record-type, and Rename Symbol is started so you can give it a meaningful name.

If an existing xsl:item-type already has the same field names, a Use record type 'name' refactoring is also offered, in the Rewrite section of the list. It sets the as attribute to the existing type without adding a declaration.

Extract record type is also offered for a record(...) type written inline in an as attribute - with the cursor on it, or a selection within it - except the whole type of an xsl:item-type. The innermost record type is replaced by the name of a new xsl:item-type, named after the field whose type it is, if any, and Rename Symbol is started:

<xsl:item-type name="person" as="record(name as xs:string, address as record(city as xs:string))"/>

becomes:

<xsl:item-type name="address" as="record(city as xs:string)"/> <xsl:item-type name="person" as="record(name as xs:string, address as address)"/>

Enumeration types

Auto-completion for values

Where an enumeration type is expected, typing a quote character offers the enumeration's values. This applies to:

  • the select of an xsl:variable, xsl:param or xsl:with-param declared with the type (or xs:boolean, for true() and false())
  • arguments of calls to user-defined functions whose parameter has the type, and typed let bindings
  • record fields with the type, in map constructors
  • the test of an xsl:when in an xsl:switch - see below

A string literal that isn't one of the values is reported as an error.

Hovering over the name of an enumeration type - or a global variable or parameter, a parameter of a function or template, or a record field, with the type - lists its values - on one line for a few values, otherwise as a list. For a type declared as another, or as a choice of enumeration types, the values are those it resolves to.

Renaming a value

Rename Symbol (F2) on an enumeration value - in its enum(...) declaration, or a string literal for it - renames the value and the string literals that refer to it: variable values, function arguments (including keyword arguments), record field values in map constructors, typed let bindings and xsl:switch cases. Find All References (⇧⌥F12) lists them.

  • Only the values of that type are renamed - not the same value in another enumeration type. An inline enum(...) type is identified by its values.
  • The value is renamed in imported modules too.
  • A new name that's already a value of the type is rejected. A quote in the new value must be doubled, e.g. don''t.

xsl:switch on an enumeration

The XSLT 4.0 xsl:switch instruction selects an xsl:when by comparing a value with each test. When the select has an enumeration type - a variable, function call or record field lookup with a declared type - the extension works with its values.

  • Missing values - when an enumeration value has no xsl:when, and there's no xsl:otherwise, the xsl:switch is marked with the information message xsl:switch has no xsl:when or xsl:otherwise for the enumeration values: .... Its two quick fixes add an xsl:when for each missing value:
    • Add missing xsl:when cases with select - e.g. <xsl:when test="'green'" select=""/>
    • Add missing xsl:when cases with content - e.g. <xsl:when test="'green'">...</xsl:when>
  • Values that never match - a test value that isn't one of the enumeration's values, or that an earlier xsl:when already tests, is a warning, as the xsl:when never matches it.
  • Auto-completion - inside an xsl:switch, the completion list offers an xsl:when for each value not yet tested.

JSON and JNodes

XPath 4.0 path expressions can navigate JSON - maps and arrays - as they do XML. The jtree() function wraps a map or array in a tree of JNodes, with a JNode for each map entry and array member, so a path such as $order/customer/name works on JSON data, with predicates, the descendant and parent axes, and the other features of path expressions.

When a JNode is declared with a record type, for example jnode(*, order), the XSLT/XPath extension knows which fields each step can reach. It checks each step, offers the field names as auto-completion suggestions, and shows each field's type and documentation on hover.

JNodes need version="4.0" and Saxon-PE or Saxon-EE 13, run with syntax extensions enabled (Quick Run enables these for a version="4.0" stylesheet). Saxon-HE 13 doesn't support XPath 4.0 syntax. In an XSLT 3.0 stylesheet, the jnode(...) item type and the get(...) node test are reported as needing XPath 4.0.

A sample project, xslt-json-schema-records, shows the features on this page in use. It converts a JSON Schema to XSLT 4.0 record types, reading the schema as JNodes, then reads JSON order data typed with the generated record types.

Navigating JSON with JNodes

A JNode tree is made with jtree(), from a map or array - for example the result of json-doc() or parse-json():

<xsl:variable name="root" select="jtree(json-doc('order.schema.json'))"/> <xsl:variable name="defs" as="jnode()*" select="$root/get('$defs')/*"/>
  • Name steps select map entries by key, e.g. $order/customer/name. * selects every entry of a map, or every member of an array, e.g. $order/lines/*.
  • get(...) is the node test for a key that isn't an NCName, such as get('$ref') or get('first name'), or for an array member by position, such as get(1). The extension reports get('a') used on its own, as a function call, as a call to an unknown function.
  • Axes work as they do for XML: $schema//get('$ref') finds every $ref at any depth, and $line/../../currency goes up from an order line, through the lines array, to the order.
  • jkey() gives a JNode's key - the map key, or the position of an array member - and jvalue() gives the value it wraps. Where a value is atomized, such as in an arithmetic expression or a text value template, a JNode gives its value, so $line/quantity * $line/unit-price works without jvalue().
  • A JNode is matched with the jnode() item type, e.g. $tree/type instance of jnode(type). jnode() is offered in auto-completion for as attributes in XSLT 4.0.
Saxon 13 doesn't support type node tests such as ~record(...) or ~xs:string in a path step, so the extension reports these as errors.

JNodes with a record type

A variable, parameter or function result declared as jnode(*, T), where T is a record type, is a JNode whose value is a T. A named item type can be used too, e.g. <xsl:item-type name="order-node" as="jnode(*, order)"/>. Child steps from the JNode are then auto-completed and checked against the record's fields, at any depth:

<xsl:variable name="order-value" as="order" select="json-doc($order-uri)"/> <xsl:variable name="order" as="jnode(*, order)" select="jtree($order-value)"/> ... <xsl:function name="ord:line-total" as="xs:double"> <xsl:param name="line" as="jnode(*, line)"/> <xsl:sequence select="$line/quantity * $line/unit-price"/> </xsl:function>
  • Auto-completion - after a /, the suggestions list the record's fields. Typing $order/customer/ lists the fields of the customer record type.
  • Checks - a step that isn't a field is a warning, e.g. Child step 'nam' - this is not a field of the record type: customer for $order/customer/nam. A ? lookup on the JNode, e.g. $order?id, is checked in the same way.
  • Hover - hovering over a field name in a step, such as unit-price in $line/unit-price, shows the field's type. Its @field text is shown too, from the xsl:item-type's documentation note. Hovering over the type name in jnode(*, order) shows the record type, with its fields and documentation.

Child steps after jtree($p)/, where $p has a record type, are auto-completed and checked in the same way.

Maps need jtree() before '/'

A / step needs a JNode on its left, not a map. Saxon 13 reports XPTY0019 for a step such as $order-value/id, where $order-value is a map with a record type, so the extension reports this as an error. The message suggests converting the map first, e.g. jtree($order-value)/id. Alternatives are a lookup, $order-value?id, or a variable declared as a jnode(*, order), as above. A step after a lookup, such as $p?address/city, is reported in the same way.

Debugging: xdm:debug() shows JNode paths

The xdm:debug() function shows a JNode's location in its tree, as an XPath path from the tree's root, above the value it wraps - in the same way it shows the location of an XML node. For an order line, this is a path such as /lines/*[2], so you can see which part of the JSON each value came from:

<xsl:message select="xdm:debug('ord:line', map { 'line': $line, 'sku': $line/sku, 'bundle': $line/bundle-items })"/>

The xsl:message output, for the second order line:

────────────────────────────── ord:line ────────────────────────────── line: /lines/*[2] { 'sku': 'KIT-7', 'description': 'Electronics starter kit', 'quantity': 1, 'unit-price': 64, 'bundle-items': [ {'sku': 'TL-1', 'description': 'Soldering iron', 'quantity': 1, 'unit-price': 0}, {'sku': 'TL-2', 'description': 'Multimeter', 'quantity': 1, 'unit-price': 0} ] } sku: /lines/*[2]/sku 'KIT-7' bundle: /lines/*[2]/bundle-items [ {'sku': 'TL-1', 'description': 'Soldering iron', 'quantity': 1, 'unit-price': 0}, {'sku': 'TL-2', 'description': 'Multimeter', 'quantity': 1, 'unit-price': 0} ]

The xdm:debug variables auto-completion for xsl:message inserts a call like this one, with every in-scope variable. See Print Debugging.

Things to know about JNodes and record types in Saxon 13

  • A jnode(*, T) type matches only an instance of T. A map with keys that T doesn't declare isn't an instance, so jtree(json-doc('order.json')) doesn't match jnode(*, order) when the data has extra properties. Converting the value to the record type first - as for $order-value above - drops the extra keys, at every depth, and fails if a required field is missing or has the wrong type.
  • No recursive item types. An xsl:item-type can't refer to itself, directly or through other types (Saxon reports SXTA0001). A field that would refer back, such as a bundle of order lines within an order line, has to be map(*) or array(map(*)) instead, so the steps after it aren't checked.
  • JSON numbers are xs:double. json-doc() and parse-json() give every JSON number as an xs:double, so a record field for a number must be xs:double - xs:integer would reject the data. A JSON null is an empty sequence, so a nullable field needs an occurrence indicator, e.g. xs:string?.
  • No ?? operator. Saxon 13 doesn't support the deep lookup operator, so use the descendant axis on JNodes instead, e.g. $schema//get('$ref').

Sample: JSON Schema to record types

The xslt-json-schema-records sample works in two stages:

  1. schema-to-records.xsl reads a JSON Schema, order.schema.json, as JNodes, and writes order-types.xsl: an xsl:item-type for the schema and for each of its $defs. Each property's description becomes an @field in the type's documentation note, so it's shown on hover.
  2. order-report.xsl includes order-types.xsl, and prints a summary of order.json, using jnode(*, order), jnode(*, line) and other typed JNodes.

Run each stylesheet with Quick Run, choosing 'None' as the XML context file, so it starts from xsl:initial-template. Then, in order-report.xsl, try:

  • typing $order/customer/ to see the customer's fields as suggestions
  • changing $order/customer/name to $order/customer/nam, to see the warning
  • hovering on unit-price in $line/unit-price, or on line in jnode(*, line), to see the documentation taken from the schema
  • changing $order/id to $order-value/id, to see the error that suggests jtree()
  • adding a property to customer in order.schema.json, running schema-to-records.xsl again, and seeing it offered after $order/customer/

The sample's README describes how each JSON Schema keyword maps to an XPath type.

Code Documentation

XSLT 4.0 adds the xsl:note element, for documentation within a stylesheet. The XSLT/XPath extension supports notes written in a simple format, xdoc-md: Markdown text followed by tags such as @param and @return, in the style of Javadoc and xqDoc.

A note in this format, as the first child of an xsl:function, a named xsl:template or an xsl:item-type, is shown in hover help wherever the declaration is used - including from other stylesheet modules - and on the declaration's own name. For functions and templates, it's also shown in signature help. For a record type, declared with xsl:item-type, the note can also describe each of the record's fields.

A module note, as the first child of the xsl:stylesheet, describes the module and its global parameters and variables - and a global parameter or variable can have a note of its own, for more detail.

The XSLT 4.0 specification allows xsl:note anywhere, with any attributes and content, and leaves the format of the documentation open. The format="xdoc-md" attribute is the extension's convention for the notes it shows: XSLT processors ignore it, with the rest of the note.

These features are enabled when the stylesheet has version="4.0" - and for XSLT 3.0, see Notes in XSLT 3.0.

Writing a documentation note

Set the format attribute to xdoc-md. The text before the first tag is a description, in Markdown. Each tag starts a new line, and continues on the following lines up to the next tag:

Tags

  • @param $name - a parameter of a function or template - or, in a module note, a global parameter
  • @return - the result of a function or template
  • @field name - a field of a record type, for an xsl:item-type
  • @variable $name - a global variable, in a module note
  • @see - a related function, template, item type, variable or URI - see References to other declarations
  • @since - the version it was added in
  • @deprecated - why it should no longer be used, and what to use instead
  • @error - an error a function or template may raise
  • @author and @version - for a module note

@field isn't an xqDoc tag: the extension adds it, in the same style, for documenting records. A field name that isn't an NCName is quoted, as in the record type - for example @field 'unit name' e.g. cm.

Markdown

The description and tag text can use Markdown: **bold**, *italics*, `code`, [links](https://example.com) and # headings.

As the note is XML, the characters < and & must be escaped as normal XML, for example &lt;. Alternatively, put text containing markup in a CDATA section: its content is shown exactly as written.

Adding a note

With the cursor on the start tag of an xsl:function, xsl:template, xsl:item-type, the xsl:stylesheet, or a global xsl:param or xsl:variable, that has no xsl:note, choose Add documentation note from the refactorings (💡 or ⌘.). A note is inserted as the first child, with:

  • an @param for each parameter, and an @return for a function (or a template with an as attribute)
  • for an xsl:item-type with a record type, an @field for each field
  • for a module note, an @param or @variable for each global parameter or variable that has no note of its own

An empty element, e.g. <xsl:item-type .../>, gets an end tag for the note.

Press Tab to move between the description placeholders.

Notes can also be added with auto-completion, after <:

  • xsl:note inserts a note on one line. It's offered within any XSLT element, and within literal result elements - XSLT 4.0 allows xsl:note anywhere.
  • xsl:note xdoc-md inserts a documentation note. It's offered where one is used - within a function, named template, item type, global parameter or variable, or at the top level for the module note - and when there isn't one yet. There, it's listed first, and preselected.

Within the start tag of an xsl:note, format is offered as an attribute, and xdoc-md as its value.

Within a note, typing @ offers the tags that apply: @see, @since and @deprecated for every note, with @field for an xsl:item-type; @param, @return and @error for a function or template; and @param, @variable, @author and @version for a module note. The note of a global xsl:param or xsl:variable is offered only @see, @since and @deprecated. After @param, the parameter names without an @param yet are offered - and likewise after @field and @variable.

Where notes are shown

  • Hover help - on a call to the function, or on the name of an xsl:call-template, the note's description and tags are shown with the signature. On the name of an xsl:with-param, the parameter's @param text is shown.
  • Hover help on item types - on a named item type where it's used, e.g. in an as attribute or after instance of, the note is shown with the type's declaration.
  • Hover help on declarations - on the name of an xsl:function, named xsl:template or xsl:item-type, the note is shown just as for a use of it. On the name of an xsl:param of a function or template, the parameter's @param text is shown.
  • Record fields - the @field text is shown in hover help on a field, e.g. r in $c?r, and with the field suggestions of auto-completion: for a lookup, a child step on a JNode, a map constructor key and an xsl:map-entry. For an item type declared as another, e.g. as="cx:point", the other type's @field text is used.
  • Variable references - on a reference to a global parameter or variable, e.g. $scale, or the name of its declaration, its type and documentation are shown - see Module notes. On a reference to a parameter of a function or template, its @param text is shown.
  • Signature help - while typing the arguments of a function call, or the xsl:with-param children of an xsl:call-template, the parameter hints show the @param text for the current parameter.
  • Auto-completion - the xsl:with-param suggestions within an xsl:call-template show the @param text for each parameter.

Notes on functions, templates and item types in included and imported stylesheets are shown too.

References to other declarations

A note can refer to a function, template, item type or variable declared elsewhere - after @see, or as a Markdown code span anywhere in the note - using the XPath syntax for it:

  • my:area#2 - the function with that arity
  • my:area() or my:area - a function of any arity - or for my:area, else a named item type or template
  • $scale - a parameter of the function or template the note documents, or else a global parameter or variable
  • template my:draw - a named template

For example, @see my:area#2, or Uses `$scale` and `template my:draw`. In a code span, a name without a prefix is only a reference as $name, name#2, name() or template name, as code spans are used for other text too.

  • Navigation - Go to Definition and hover help work on a reference just as on a use of the declaration, including declarations in imported and included modules.
  • Find references and rename - the references in notes are found, and renamed, with the declaration - e.g. renaming my:area changes @see my:area#2 too.
  • Auto-completion - after @see, and within a code span, the declarations are suggested, written so that they refer to them: parameters and variables, e.g. $scale, functions by arity, e.g. my:area#2, then item types and templates.

Module notes

A documentation note as the first child of the xsl:stylesheet (or xsl:transform or xsl:package) describes the module. Its tags can describe the global parameters and variables briefly, so they don't need notes of their own:

<xsl:stylesheet ... version="4.0"> <xsl:note format="xdoc-md"> Draws shapes. @param $scale the scale factor @variable $origin the point all shapes start from @author Ann @version 1.2 </xsl:note> <xsl:param name="scale" as="xs:double" select="1"/> <xsl:param name="colour" as="cx:colour" select="'red'"> <xsl:note format="xdoc-md">The fill colour, used for **every** shape.</xsl:note> </xsl:param>

For more detail, a global xsl:param or xsl:variable can have a documentation note of its own, as its first child. It's shown in place of the module note's @param or @variable text - so a module note can give a brief summary, and the parameter's own note the details.

  • Hover help on variables - on a reference to a global parameter or variable, or the name of its declaration: its type, its documentation, and for an enumeration type, its values.
  • Hover help on imports - on the href of an xsl:import or xsl:include: the module's note, and its path.
  • Preview - on the start tag of the module note: the note as it's shown for an import of the module.
  • Rename - renaming a global parameter or variable renames its @param or @variable tag too.

Notes in XSLT 3.0

Unless you're using a compatible Saxon version with syntax extensions enabled (see note below), an XSLT 3.0 processor reports XTSE0010 for xsl:note, as an unknown XSLT element - the workaround is just to exclude this with use-when="false()", which works with any processor. In a stylesheet with version="3.0":

  • an xsl:note without a use-when attribute is a warning, with the quick fix Exclude with use-when="false()"
  • the xsl:note completions and Add documentation note insert the note with use-when="false()"
  • documentation notes are shown, highlighted and checked, as in XSLT 4.0
Saxon PE and EE 12.8 or later, run with syntax extensions, accept xsl:note in an XSLT 3.0 stylesheet. With the setting XSLT.validation.xslt30ItemTypesAndNotes, the linter recognises notes so they need no use-when, and XSLT 4.0 xsl:item-type declarations are fully supported too - see XSLT 4.0 Item Types and Notes in XSLT 3.0.

Highlighting Details

The content of a note is highlighted as documentation: tags, parameter and field names, code, bold and italic text, headings and links each have their own semantic token type. The token types have fallbacks, so they're highlighted in most color themes. To change their colors, add rules for the token types xdocText, xdocTag, xdocParam, xdocCode, xdocBold, xdocItalic, xdocHeading, xdocLink and xdocCdata to the editor.semanticTokenColorCustomizations setting.

Notes as XML

The extension includes an Invisible XML grammar for its documentation notes, xdoc-md.ixml. With the XPath 4.0 invisible-xml() function, a stylesheet can use it to turn its notes into XML - for example, to generate documentation for a library of functions.

Tag Checks

The @param tags are checked against the xsl:param elements of the function or template, and the @field tags against the fields of the item type's record type:

  • an @param for a name that isn't a parameter, or an @field for a name that isn't a field, is a warning
  • a second @param for the same parameter, or @field for the same field, is a warning
  • when a note has @param tags, parameters without one are reported as information, with an Add missing @param quick fix - and likewise fields without an @field, with an Add missing @field quick fix
  • an @field in the note of a function or template, or of an item type that isn't a record type, is a warning
  • an @param, @return or @error in the note of an xsl:item-type is a warning
  • an @see reference that refers to no declaration, e.g. @see my:aera#2, is a warning - but not other text, e.g. a URL, or a built-in function or type, e.g. fn:sum#1

In a module note, the @param and @variable tags are checked against the global parameters and variables in the same way: when the note has @variable tags, global variables without one are reported as information, with an Add missing @variable quick fix - as for @param, with Add missing @param. A global parameter or variable with a note of its own isn't reported as missing from the module note. @return and @error in a module note, and @param, @variable, @return and @error in the note of a global parameter or variable, are warnings.
